Closing Studio safely while work is still running

STU-02 teaches why a window must not disappear before the work it owns has reached a safe state.

A simple example

You start a build and immediately click the window close button. The compiler may still have output to deliver, Test Explorer may still own discovery data, or the debugger may still own a child process. Destroying the window first can leave callbacks pointing at objects that no longer exist.

New rule: Studio closes admission first, requests owned work to stop, keeps the window alive, and asks you to close again after the work has reached a stable state.

What happens when you close

SituationStudio action
Test run or discovery activeRequest cancellation/stop and keep the window open.
Build activeRequest build cancellation and keep the window open.
Debugger activeRequest debugger termination and keep the window open.
No running work, unsaved documents existAsk whether to discard the unsaved edits.
No running work and no unsaved documentsAllow the normal GTK close.

Why there are 256 fixture files

The close planner has eight externally visible yes/no inputs. There are exactly 256 possible combinations. This batch stores every combination as an inspectable acceptance fixture and runs them through the same native planner. These are not duplicate filler files: together they form the complete truth table for the STU-02 close contract.

Try the native planner

umicom-studio-close-plan --self-test
umicom-studio-close-plan mask 255

The command does not close a window or terminate a process. It only explains the deterministic decision.

Windows acceptance exercise

  1. Open Studio with two edited Notes files.
  2. Start a deliberately slow Debug build.
  3. Click the window close button.
  4. Confirm that Studio stays visible and reports that work is stopping.
  5. After the build reaches a final state, close again.
  6. Confirm that the unsaved-document dialog appears only after running work has stopped.
  7. Repeat while a debugger session is active and while Test Explorer is discovering tests.
