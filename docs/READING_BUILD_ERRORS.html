Reading and fixing compiler errors in Umicom Studio

A failed build is useful information. It tells you that the compiler could not translate the saved source, and usually gives a file and line to investigate. This lesson follows one small mistake in an Umicom Notes project so that you can practise finding the cause without losing other work.

1. Begin with a working Notes project

Open a disposable Umicom Notes project, or create a C23 Console Application with File → New Project. Keep your real application code separate from this exercise. Open src/main.c and enter the following program.

#include <stdio.h>

int main(void)
{
    unsigned savedNotes = 3U;
    printf("Umicom Notes: %u saved notes\n", savedNotes);
    return 0;
}

savedNotes is an unsigned whole number. The program prints it and returns zero to report normal completion. At this stage it displays a count; it does not create or load note files.

Save the file, review Build → Project Settings, and build the project. Check the selected source folder, compiler and executable before using Run. Grant workspace trust only after reviewing the project: its build files can execute programs.

2. Introduce one controlled error

Remove the semicolon after 3U and save again:

    unsigned savedNotes = 3U
    printf("Umicom Notes: %u saved notes\n", savedNotes);

Build the project. The compiler cannot interpret the unfinished declaration correctly. It should report an error and the build should fail. Read the first relevant diagnostic before changing anything else; a single missing symbol can produce several later messages.

3. Read the message

A compiler diagnostic describes a problem found while translating source. For example:

C:/Umicom Notes/src/main.c:6:5: error: expected ',' or ';' before 'printf'

The path identifies the source file. 6 is a one-based line number; 5 is the reported column. Error is the severity. The remaining words explain what the compiler was trying to read.

The highlighted line is a starting point, not always the line that contains the mistake. Here the compiler notices the difficulty when it reaches printf, but the missing semicolon is on the previous line. Look at the surrounding code instead of mechanically changing the highlighted token.

Warnings identify code worth investigating even when compilation succeeds. A note often explains a related declaration. A fatal error stops a compilation stage. Exact wording differs between compiler versions.

4. Move from Problems to the source

Open Problems. Select a row and choose Open, or activate the row. Studio uses the diagnostic's retained identity to open its source document. Previous and Next move between available source locations and wrap at either end.

If the file is already open, its existing working copy is selected. Unsaved text is not replaced with the file on disk. Try keeping a second tab with an unsaved note open while you navigate.

A linker or tool failure may have a message but no source location. Read Output for those messages. The panel shows up to 300 active rows; source navigation can still visit the other retained source problems. Clearing Problems does not change any file or fix a compilation error.

5. Correct the source and rebuild

Restore the missing semicolon, save the file, and build again. A newly collected compile result retires earlier build findings from the same producer; findings from unrelated tools remain independent. Read the latest Output result before using Run.

There is no need to recreate the project or reset Git for a missing semicolon. The normal cycle is edit → save → build → read → correct. Once the program builds successfully, run it and check:

Umicom Notes: 3 saved notes

Repeat with a misspelt variable name, such as saveNotes in the printf call. Predict which line will be reported before compiling.

6. Understand location limits

Source paths from a normal CMake compilation are resolved relative to its build directory, not the directory from which Studio started. Configure-time paths are resolved from the source directory. Custom tools that change into nested directories should emit absolute source paths; the reader does not infer every tool's working-directory changes.

Columns are currently interpreted as one-based UTF-8 byte columns. In ordinary ASCII code without tabs, byte and displayed columns agree. GCC may report display columns by default, so tabs or non-ASCII characters can shift the apparent caret. For a GCC project that needs exact byte columns, add the compiler option -fdiagnostics-column-unit=byte after checking that the compiler supports it. The GCC diagnostic options explain this distinction.

If you changed the source after the build, a diagnostic can refer to an older line. Rebuild to refresh it. A missing source file, a source path too long for the Problems record, or an unsupported URI has no automatic Open action. Inspect the transcript rather than guessing another file.

7. Compare with a terminal build

Use your practice project's directory, not the directory used to build Studio itself. On Windows, a generated project can be built with:

Set-Location "C:\umicom\projects\umicom-notes"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
cmake --preset windows-ucrt64-debug
cmake --build --preset windows-ucrt64-debug --parallel 2

On Linux, use the project's own preset or explicit directories:

cd "$HOME/umicom/projects/umicom-notes"
cmake -S . -B build/linux-debug -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build/linux-debug --parallel 2

Run one line at a time and stop on an error. Studio and the terminal must compile the same saved source. An old executable is not evidence that a failed build succeeded.

Continue practising

When you can explain each part of a compiler message, try moving a function into a second source file. Introduce and repair one compiler error, then one linker error caused by omitting the new file from the build. Compare their messages and why only one necessarily identifies a source line.
