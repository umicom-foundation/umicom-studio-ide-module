Umicom Studio IDE User Guide

Studio brings source files, projects, build tools, a debugger, a project board and learning material into one workspace. Umicom Framework owns the shared document, workspace, build, debugging and learning services. Studio supplies the menus and panels through which you use those services.

Studio is under active development. A visible option does not mean its external tool is installed or that every integration is available. This guide describes the controls and results to check. If a step does not produce its stated result, keep your files and capture the failure; do not assume the operation succeeded.

1. Find your way around

An IDE, or integrated development environment, combines tools used to make software. A project is a folder containing related source files and instructions for building them. A workspace is Studio's view of that project and its panels.

  1. Start Studio. The Welcome page offers New File, Open File, Create New Project and Open Project Folder.
  2. Explorer shows the open project's files. Code Editor shows documents. Output records tool output; Problems lists diagnostics such as compiler errors.
  3. Choose a panel from View, or the window catalogue. Opening an existing panel should focus it rather than create a duplicate.
  4. Use the layout controls to enter editing mode before rearranging panels. Drag a divider to resize neighbouring panels. Save an arrangement when you want to retain it. Lock the layout to avoid accidental rearrangement.
  5. Closing a panel hides that view. Closing a source document is a separate operation under File > Close Editor. Closing a panel must not discard unsaved source.

Grey controls are unavailable in the present state. Save needs an active document, a build needs a configured project, and Continue needs a paused debugger. An enabled control that does nothing is a defect, not a normal prerequisite.

2. Create, open, edit and save files

Create a file and choose where it lives

  1. Choose File > New File, or press Ctrl+N. An editable source document should appear.
  2. Click inside the editor and type a few lines. The document becomes dirty, meaning its text has not yet been saved.
  3. Choose File > Save As.... Select a folder you can access and a filename such as notes.c. This is where your work is saved.
  4. Choose Save. The dirty marker should clear only when saving succeeds. Reopen the file to check the saved text.

Open and switch between existing files

  1. Choose File > Open... or Ctrl+O. A file picker should appear. Cancel leaves existing documents unchanged.
  2. Select a local text file. Wait for opening to complete. File > Opening Results shows per-file failures when a selection cannot be opened.
  3. Open a second file. Select each document tab and type different text into each one. The selected tab must own the visible text, selection and save operation.
  4. Use Save or Ctrl+S for the active file; Save All saves open dirty documents. Inspect the completed result before closing.

Save Copy... creates a separate copy while keeping the original document's path and state. It differs from Save As. If a destination exists, do not assume it will be replaced: read the result and choose a new name when required.

Close safely

  1. Choose File > Close Editor. For an unsaved change, use the offered Save, Discard or Cancel decision.
  2. Cancel keeps editing. Choose Discard only when you intend to lose that unsaved change.
  3. Close All Source Documents and Close Other Source Documents apply the same decisions across documents. Cancellation must preserve remaining open work.
  4. Reopen Closed Document returns to a retained saved path. It is not a substitute for saving an unsaved draft.

Reload from Disk... reads the file again. Review the conflict decision if your editor contains changes. Undo and Redo change active editing history; they do not reverse external file changes.

3. Create a small C project

C source is readable program text. A compiler translates it into machine code. A linker joins compiled pieces into an executable. CMake describes the build; the selected build tool runs the compiler and linker steps.

  1. Choose File > New Project. Select the C console template, a project name and a new destination folder of your choice.
  2. Create the project and inspect its files in Explorer. Avoid a destination containing important existing work.
  3. Open src/main.c. If the template uses another source filename, use the file listed by its CMakeLists.txt.
  4. For a minimal exercise, use this program. Retain your project's own header and licence when adapting an existing file.
/* Print a message, then return a successful exit status. */
#include <stdio.h>

int main(void)
{
    puts("Hello from Umicom Studio");
    return 0;
}

#include makes standard input/output declarations available. main is where this console program begins. puts writes a line. Returning zero tells the operating system the program finished successfully. This exercise uses the same document, build and process services as larger Umicom projects.

For an existing project, choose File > Open Folder... and select the source folder containing its build description. Opening a folder and trusting its build scripts are separate decisions.

4. Configure, build and run

  1. Install a C compiler, CMake and a build tool supported by your project. On Windows UCRT64, start Studio with that toolchain's bin directory on PATH. Studio does not inherit environment changes made after it started.
  2. Choose Build > Project Settings. Review source and build folders, configuration, tool paths, target and executable. A build folder contains generated files, separate from source.
  3. Review the project before granting workspace trust. Build descriptions can execute programs.
  4. Save the source. Choose Build > Configure and wait for its completed result in Output. Configuration prepares build instructions; it does not produce the application.
  5. Choose Build > Build. Wait for a successful completed result. A queued or accepted request is not a successful build.
  6. Choose Run > Run. Inspect output and exit code. The Build panel also separates Build and Run from its launch-only action. Launch-only requires an existing executable from the intended build.
  7. Change the message, save and repeat Build and Run. The new message should appear. Otherwise check the active project, executable and build output.

Rebuild deliberately rebuilds more work. Use ordinary Build for incremental development. Shared headers or configuration changes can correctly affect many targets. Clean removes generated outputs according to project rules; it is not needed before each build. Cancel Build requests cancellation; wait for completion before conflicting operations.

Install, Package and Deploy need corresponding project rules and destinations. They are not interchangeable with Run. Review their target directories and results.

Practise diagnosing an error

  1. Temporarily remove the semicolon after puts(...), save and Build.
  2. Expect failure. Open Problems and select the source diagnostic. The relevant file and line should be revealed.
  3. Restore the semicolon, save and Build again. The new successful result should be distinguishable from the earlier failure.

5. Debug a program

A debugger pauses a running program for inspection. A breakpoint requests a pause at a source line. A debug adapter connects Studio to an installed debugger. Installing a compiler alone does not guarantee the required adapter is available.

  1. Build with debugging information, normally a Debug configuration. Select this project's executable.
  2. Open Debug controls from the workspace's window catalogue. Choose a supported adapter kind and executable path, then Use adapter. Review setup status.
  3. Set a breakpoint on the puts line using breakpoint controls. The adapter must verify the requested breakpoint before you rely on it.
  4. Choose Run > Debug or Start in Debug. Wait for a stopped event. Inspect the source line, threads and stack frames.
  5. Step Over executes a statement without entering a called function; Step In enters a call; Continue resumes execution. Availability depends on adapter capabilities and stopped state.
  6. Choose Stop, verify the session ends, then edit source to check Studio remains responsive.

Attach requires a deliberately selected process and an adapter supporting attachment. Use your exercise process. Protocol fixtures cannot establish that a particular installed debugger works; qualify the real toolchain separately.

6. Run project tests

A test checks a defined behavior against an expectation. Tests belong to a configured project and build directory.

  1. Configure and build with project tests enabled.
  2. Open View > Test Explorer, then Test > Discover Tests. Wait for discovery and check the active project owns those tests.
  3. Select a test and choose Run Selected, or Run All Tests. Read the completed outcome and captured output.
  4. After fixing a failure, use Rerun Failed. Check the new result rather than hiding the earlier failure.
  5. Stop Tests requests cancellation. Skipped, cancelled and not-run tests are not passes.

Coverage and debugging selected tests require compatible tooling. Missing providers must remain unavailable or return an explicit unsupported result.

7. Open and close the project board

A Kanban board organises work into cards and columns. It is separate from source documents and does not compile a project.

  1. Open a project folder. In Explorer choose Project board.
  2. Expect a board associated with that project. Opening it again should reuse the same window.
  3. Use explicit board storage controls to choose a location, then create or open a board. Keep private plans outside folders intended for public publication.
  4. Create a card, assign a developer and move it between available columns. Save and confirm completion.
  5. Close with the window close button. Resolve any unsaved-work decision. A clean board should disappear from the application's window list.
  6. Return to Studio and create a new file. Reopen Project board and check the intended board opens and Studio stays responsive.

If a board refuses to close, record whether a save or unsaved-change prompt is active. Repeatedly opening more boards is not a repair.

8. Open lessons and guides

  1. Choose Help > Studio User Guide or Read the Studio user guide on Welcome.
  2. The local learning catalogue opens. If it reports no matching pack, choose a folder containing the supplied learning-pack.json, then Load learning pack.
  3. A source build prepares Studio's pack beneath its learning-pack build folder. Installation places it beneath share/umicom-studio/learning-pack. Choose the actual folder, not an arbitrary parent.
  4. After loading completes, choose the guide again. The reader verifies the resource against the pack before displaying it.
  5. For lessons, open Guided Learning and choose a lesson-library folder. Reading does not grant project trust or execute an example.
  6. Create practice projects in a destination you choose. Close the reader and check source documents remain unchanged.

The reader does not silently replace missing content with an internet page. Select a moved library's new location. A browser can also open this HTML guide directly.

Current integration limits

Studio is under active development. A menu label alone does not mean its workflow is ready. Run configuration selection, Run Stop/Restart, Attach, the breakpoint-manager entry, symbol navigation, branch management, general Settings, Extensions, Toolchains, Code Guard, some Window arrangements and Help utilities still require native integration or qualification. Use the existing Build and Debug panel controls where available; an unavailable entry must not report success. The acceptance checklist records these gaps explicitly.

In particular, protocol-level debugger tests do not prove that an installed debugger can stop at a real source breakpoint. Mouse input, typing, file choosers, board closure and continued editing require native acceptance in the built application.

10. Troubleshoot an unresponsive command

  1. Record the exact action, expected result and visible outcome. Distinguish disabled controls from enabled controls that do nothing.
  2. Check for a dialog behind Studio, pending save, build or debugger session.
  3. Inspect Output and Problems if possible. Acceptance differs from completion.
  4. Save accessible work. Preserve files, settings and logs for investigation.
  5. For a reproducible click failure, launch from a console with action tracing. Logs may contain paths; review before sharing.

Use a new timestamped log folder. This PowerShell example assumes the source build shown; adjust to your executable. Stop if it is missing.

Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
$StudioLog = "C:\umicom\_local\logs\studio-$(Get-Date -Format yyyyMMdd-HHmmss)"
New-Item -ItemType Directory -Force $StudioLog
$env:UMICOM_STUDIO_TRACE_ACTIONS = "1"
try {
    & ".\build\windows-ucrt64-all-debug\bin\umicom-studio-ide.exe" 2>&1 |
        Tee-Object "$StudioLog\runtime.log"
} finally {
    Remove-Item Env:\UMICOM_STUDIO_TRACE_ACTIONS -ErrorAction SilentlyContinue
}

Report inaccessible editing, a missing picker, a tab showing the wrong text, and a stuck board separately. Include the executable path and its build revision so an older executable is not confused with newer source.
