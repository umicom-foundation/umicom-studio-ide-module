Browse large test lists

Studio displays up to 300 matching test rows per page. Previous page and Next page let you reach rows beyond the first page without changing the discovered tests or starting a test run.

  1. Open Test Explorer and use Discover for the project’s configured build directory.
  2. Read the range below the filters. “Page 2 of 4 — rows 301–600 of 907 matching” means that the displayed rows are only part of the filtered list.
  3. Use Next page or Previous page. The buttons are disabled at the ends of the list.
  4. Use the search field, Failed only, Group or Sort to change the list. Changing one of these controls returns to the first page.
  5. Use Select to inspect a test’s retained evidence. Run and Debug select that row before dispatching the existing operation. Source opens its discovered location.

When results or discovery change

A routine refresh keeps the same page when it still exists. If the list becomes shorter, Studio moves to the last available page. Unchanged pages keep their existing native rows instead of rebuilding them on each refresh.

Controls from an older page cannot act on a newer test list. If discovery changes just before you click Next page, that click refreshes the current page first. Review it and click again to move. If a refresh is interrupted by a changed filter or closed window, the partial page grants no row actions; the next refresh publishes the current list.

Jump across a large catalogue

  1. Choose Last page to inspect the final matching rows directly. The Framework clamps the request to the current catalogue.
  2. Choose First page to return to its start. First and Previous are unavailable at the beginning; Next and Last are unavailable at the end.
  3. Change the search or view options to start again at the first matching page. A discovery change refreshes stale navigation before accepting another move.

Read outcomes accurately

The summary counts all discovered rows in the current Framework projection. The range counts matching rows; the “showing” count is the number on this page. Hierarchy parents can appear with matching descendants. The existing model groups timeouts with failed counts and cancellations with not-run counts; each row still displays its exact retained outcome. A skipped or not-run result is never converted to a pass.

Limits and recovery

The Framework projection accepts up to 65,536 discovered records, including hierarchy parents. Pages show at most 300 matching rows. Selection remains bounded to 1,024 IDs and retained result storage to 4,096 records. Run All and Failed keep their service scope; they do not mean “this page,” and large-catalogue browsing does not prove that a complete execution history fits.

  1. If the range reports a capture or memory error, inspect the discovery message and selected build directory. The previous model survives a failed rebuild, but Studio grants no row actions until it can publish a current page.
  2. If the catalogue exceeds the displayed model maximum, configure a smaller suite or use CTest against the configured build directory.
  3. For metadata inspection outside the workbench, use the metadata discovery command. Legacy text discovery has a separate, smaller limit.

Changing pages does not remove tests, retained results, source files or command drafts. See run-specific evidence to inspect one retained execution.
