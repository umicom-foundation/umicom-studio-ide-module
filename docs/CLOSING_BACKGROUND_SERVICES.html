Close Studio background services safely

Studio uses shared Framework services to watch project files, run processes and execute background tasks. Those services can still refer to documents, settings, diagnostics and workspace models while the user is closing a window. The lifecycle controller must finish background work before releasing the models that work can access.

Understand ownership

The Studio bootstrap owns the application composition. Its service graph owns the watcher, process supervisor and task queue. Getter functions return borrowed pointers: they let a component use an existing object, but do not transfer permission to destroy it. A component must not release the service graph merely because it can obtain a pointer to it.

The API UmiStudioServicesStopBackground stops the watcher, shuts down supervised processes, then closes the task queue. It preserves the queue's existing policy: cancel pending tasks and wait for running tasks. Running tasks must cooperate and eventually return. This API does not forcibly terminate a callback and does not promise a bounded shutdown duration.

Use checked release at the ownership boundary

  1. Close admission to new UI actions and arrange for outstanding commands to finish or cancel according to their own contract.
  2. Exclude other UI, registry and service users. Checked release is not a replacement for that application-level ownership discipline.
  3. From an external controller, call UmiStudioBootstrapRelease(&bootstrap).
  4. On success the bootstrap pointer is cleared. On failure retain the pointer and report the returned status; do not resume ordinary work on a partially closing graph.
  5. Retry release after the cause can be addressed. Successful steps may already have stopped children or released models, so a retry continues with the retained state rather than constructing a replacement over it.
UmiStatus close_status = UmiStudioBootstrapRelease(&bootstrap);
if (close_status != UMI_STATUS_OK) {
    /* Keep the owner and report close_status. Do not free it manually. */
    return close_status;
}

For a service graph owned without a bootstrap, use UmiStudioServicesRelease(&services). Do not independently release a graph borrowed from a live bootstrap. Both release functions accept an empty owner as a successful no-op; passing NULL instead of pointer storage is an invalid argument.

A task cannot destroy the graph executing it

Waiting for the current task queue from one of its own workers would wait on that same worker. Framework exposes UmiTaskQueueIsCurrentWorker so Studio can refuse such a request before stopping unrelated services. Checked Studio release returns UMI_STATUS_INVALID_STATE in this case. Request shutdown through the application's controller and let the callback return normally.

The older void destroy functions remain compatible entry points. They retain the graph when checked shutdown fails, but cannot return the error to a caller. New ownership code should use checked release. A void return is not evidence that the graph was freed.

Keep a failed close checkpoint pending

Stopping modules and recording a clean recovery checkpoint are distinct operations. Studio records a pending session-close obligation when a session starts. If checkpoint creation fails after modules stop, another stop call retries the checkpoint. Starting another session is refused until the pending close succeeds.

The recovery checkpoint discussed here is the Framework session model. Its clean flag is not proof that every separate document, recent-items file, external process or disk write was saved. Each persistence owner still has its own save and error-handling contract.

Retain Framework cleanup after failed startup

A failed Framework startup may still have rollback work to finish. Studio checks UmiMasterControllerNeedsStop even when its own started flag was never set. Checked master release also reports failure before the service graph can be freed. Module stop errors and service shutdown errors remain separate results.

Read the regression examples

tests/test_service_lifecycle.c creates a service graph with repository discovery disabled. Each CTest case has its own working directory, so session data does not belong to an editor's project or another test. The ordinary cases cover empty owners, service release, bootstrap release, repeated session cycles and self-release attempts from queue workers.

Build umicom-studio-service-lifecycle-test in an Applications build with Studio and testing enabled. Run CTest with -R "^studio[.]services[.]lifecycle[.]" --output-on-failure --no-tests=error. The Linux GNU/Clang target umicom-studio-service-lifecycle-fault-test adds selected stop, release, Framework controller and checkpoint errors. Its tests use the studio.services.lifecycle-fault. prefix. An error must retain the owner, and retry must complete the outstanding operation.

These service tests do not qualify window-manager behaviour or all graphical close paths. Also exercise the normal Studio application: open a project, start an ordinary build, request cancellation where available, close Studio and inspect its runtime log. A reported background-service close error is a failed shutdown requiring investigation, even if the window has disappeared.

The shared contracts live in Framework's include/umicom/platform/task_queue.h, include/umicom/platform/watcher.h and include/umicom/platform/process_supervisor.h. Studio keeps composition policy in src/app/services_lifecycle.inc and src/app/bootstrap.c.

Bootstrap release also refuses reentry from a Framework owned-service destructor before touching UI or background services. Run studio.services.lifecycle.service-destructor to check this parent-ownership boundary. After partial release, retry closure rather than restarting the retained bootstrap.
