Use private test history in Umicom Studio

The Test Explorer can save completed queued runs in a local SQLite database. Saved evidence belongs to its original run. Opening history does not rerun tests, recover a running process, or mark the current source files as passed.

Save a completed run

  1. Open Test Explorer and expand Private test history.
  2. Choose an absolute filename in a private existing directory outside your source repositories. For example, use a personal application-data directory rather than a project folder. Enter the filename and select Open archive. Studio creates the database if needed. The parent directory must already exist.
  3. Run tests through the Test Explorer and wait for result publication to finish.
  4. Leave Retain diagnostic text off to save outcomes without output. Enable it only when the bounded output tail is useful and suitable for your private database. Names, paths and results are saved in either case. The database is not encrypted and no automatic redaction is promised.
  5. Select Save completed run. Studio saves on a worker so the window remains responsive. The status shows the committed saved run ID, or the reason a save did not complete.
  6. Select Refresh saved runs to view the catalogue. A failed save leaves the actual test results unchanged.

Studio captures the source root and workspace generation accepted with the run. It currently does not capture a Git revision or a hash of the tested executable. The catalogue says when a revision was not captured. Source edits after the run do not change saved evidence.

Read a saved attempt

  1. Find a saved run's ID in the catalogue and enter it in Saved run ID.
  2. Enter a completed attempt number starting at 1. For a repeated selection, attempts follow the original selection order for each repeat.
  3. Select Read saved attempt. Studio displays its test name, ID, build directory, configuration, outcome, exit code and duration. It displays the diagnostic tail only if that run retained it.

“Skipped”, “cancelled”, “timed out” and “not run” remain distinct outcomes. “Never started” means the run ended before reaching those planned attempts. An empty successful catalogue means no runs were saved; it does not mean tests passed.

Restart, detach and remove

  1. After restarting Studio, reopen the same private database filename. Its selection is not written into your project files.
  2. Use Detach to close the attachment while keeping the database on disk.
  3. To free space, enter the exact saved run ID and select Remove this saved run. This removes that archive record and its saved results; it does not delete source files or change the current Test Explorer results.

One archive scope holds up to 32 runs and never evicts records automatically. A duplicate save of the same accepted job in one attachment is refused. Reopening an attachment resets that session-local duplicate check.

If something goes wrong

BUSY: wait for the current run or save to finish. New queued runs cannot replace a job while it is being saved. Stop save requests cancellation; a commit that already succeeded remains saved. Closing the window during a save requests Stop and asks you to close again afterward, keeping the worker's borrowed data alive.

Invalid path: use an absolute filename with a valid parent directory. An unsuccessful replacement leaves the previous archive attached. Storage or parse error: retain the database for inspection and choose a different file if necessary. Do not erase evidence merely to make the error disappear. If commit or rollback reports an I/O error, reopen and inspect the saved records before retrying; an uncertain storage outcome is not proof that nothing was written. SQLite unavailable: use a build that includes the Framework SQLite adapter.

Opening, listing, reading and removing records are explicit database operations and may take longer on slow or contended storage. Use a local private location. The periodic UI refresh reads only worker state. Saved runs are not a complete CI history or a signed release qualification.

Compare saved test runs

  1. Open your private archive and choose Refresh saved runs to find two run IDs.
  2. Enter the newer run in Saved run ID and the earlier run in Baseline run ID for comparison.
  3. Choose Compare saved runs. The database is read in the background. Use Stop comparison if you no longer need the result.
  4. Read the summary and the first page. A page contains at most 100 named tests. Enter another page number and choose View comparison page to continue.
  5. For a changed test, use Read saved attempt with the original run ID to inspect any diagnostic output retained when that run was saved.

A new failure requires a complete passing baseline under the same recorded conditions. Source-root changes, repeat counts, early-stop policies, timeouts and enabled flags are shown separately. Cancelled, skipped and never-started attempts are never treated as passes. Discovery IDs may change; matching uses test name, configuration and exact build directory.

The summary includes all rows, even those on other pages. Rows show counts for both runs and their total recorded durations. A copied comparison remains available if you remove one of its saved runs, until you compare again or detach the archive. Reopening an archive clears the previous comparison.

If a run is missing, or storage is corrupt or busy, Studio reports the error without changing live test results. Closing during archive work requests cancellation first; close again after it finishes. Comparison results describe historical observations, not the current checkout or verified source fingerprints.

Read history while keeping Studio responsive

  1. Choose Open archive after entering an absolute filename in a private directory. Studio opens the database and checks its catalogue in the background. The existing archive remains attached until the replacement is ready.
  2. Choose Stop opening if the selected file is no longer wanted. Wait for opening to finish before detaching or trying another file. A late Stop still prevents attachment if the UI has not published the replacement. Any database file already created remains on disk.
  3. Choose Refresh saved runs. Studio reads the catalogue on a Framework worker, then updates the history pane when the observation is complete.
  4. Enter a saved run ID and an attempt number, starting at 1, then choose Read saved attempt. The displayed origin, test request and outcome come from the same database observation.
  5. Choose Stop reading to cancel a pending read. Wait for the read to finish before detaching the archive or starting another archive operation.

The Context line compares recorded project and build settings with the current profile. Studio captures those settings when the test run is accepted, so switching profiles before saving cannot relabel an older run. Source files, test binaries, preset-file contents and compiler versions are not captured by this view.

Comparing saved runs also shows whether the ordered selection matches. Matching selections can still produce different outcomes, and matching outcomes do not certify the current checkout. Older entries without fingerprints are labelled as unrecorded.

If a read reports a missing row or damaged record, keep the database for investigation. Studio leaves the existing text pane intact and does not manufacture a passing result. Saving diagnostic text remains optional because logs may contain private information.

If opening reports a damaged catalogue or a storage error, the previous attachment and live test results remain unchanged. Correct the path or storage problem and choose Open archive again. The path is copied when the request starts: editing the field does not redirect work already running. Closing a previous attachment can still perform synchronous storage cleanup. Saved-run removal now runs on the Framework task queue.

Remove a saved run

  1. Check the saved run ID in the history pane. Enter that exact ID in the saved-run field.
  2. Choose Remove this saved run. Studio copies the ID and queues the removal. Editing the field afterwards cannot redirect that request. Other archive operations wait until it finishes.
  3. If you change your mind, choose Stop removal. Cancellation can stop the transaction before it commits; it cannot restore an already committed removal.
  4. Wait for the completion message. When removal commits, Studio refreshes the saved-run list. Source files and current test results are unchanged. The database file remains on disk.

If no commit is confirmed, refresh the list after the operation finishes and read the reported error. A busy archive can be retried later. For damaged records or storage failures, preserve the database for investigation. Removing the most recently saved completed run lets you save that live run again; the new saved run receives a new ID.
