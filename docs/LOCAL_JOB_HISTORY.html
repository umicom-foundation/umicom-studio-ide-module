Reviewing local build-job history

Local job history keeps the outcome of a build workflow after Studio closes. It complements the live Output view and optional build log. It does not save compiler output, command arguments, credentials or the build profile.

Open a private history file

  1. Finish the current build and let Studio collect its results.
  2. Open the Output surface and expand Local job history.
  3. Create a private folder outside your source repositories, then enter an absolute database path in that folder. For example, choose a file inside your personal application-data directory. The parent folder must exist.
  4. Click Open history. Studio opens or creates that SQLite file. The status shows the accepted path. Typing a different path alone does not change the active database.
  5. Use Studio's normal configure, build, test, install or launch workflow. The existing project trust and profile checks still apply.
  6. After the workflow finishes, click Refresh saved jobs to see saved outcomes.

Use one history file per project. The record caption identifies the requested workflow, such as Build or Test, rather than persisting a potentially sensitive project path.

Review after restarting

  1. Reopen the project and the Output surface.
  2. Enter the same private database path and click Open history.
  3. Read the saved outcomes. A finished record shows success, failure or cancellation. An unfinished record says its outcome is unknown outside its original session.
  4. Inspect the build folder, saved log or installed files before deciding what to do next. Start any new workflow explicitly through Studio's normal controls.

Opening history never resumes a build or launches an application. Studio does not automatically remember the database selection; choose it again when reopening the project.

Manage retained records

Remove finished records deletes successful, failed and cancelled metadata from the selected history. It retains unfinished evidence. It does not delete log files, build artifacts or source files. A history scope holds up to 64 records and refuses new recorded jobs when full. Preserve a full database before selecting a different private file if unfinished records occupy every slot.

Detach history returns future jobs to the existing in-memory workflow. The database stays on disk. Attachment, refresh and removal are refused while a job is active or has results still waiting to be collected.

If something goes wrong

  • Unavailable: the current Framework build may lack SQLite support. The normal build workflow remains available without persistent history.
  • Busy: wait for the active job or competing database operation, then review again. A refused database replacement leaves the previously selected history attached.
  • Storage error: inspect free space and folder access. Framework stops later build phases after a failed checkpoint. Completed phase results remain visible, but a final saved outcome may be missing.
  • Malformed history: preserve the file. Studio refuses it instead of discarding unknown records. Select a separate private history file only after reviewing the problem.

Job metadata is local and is not encrypted by this feature. Keep the database in a private folder and out of Git. Saved history is evidence of what Studio recorded, not proof that an external process is still running or that interrupted work can safely be repeated.

Understand the project comparison

  1. Open the project and select the build settings you intend to use.
  2. Open Output, expand Local job history, and open the private SQLite file used for your earlier jobs.
  3. Choose Refresh saved jobs. Each entry shows its recorded outcome and a separate Context explanation.
  4. If you see Different project or resource, the entry belongs to another project root. Different settings means at least one reviewed profile value has changed. Neither entry qualifies the current selection.
  5. Same settings; input contents not recorded confirms only the settings comparison. Save the intended sources and request a new build and test run to check your edits. The comparison does not inspect source contents, preset file contents, tool versions or environment changes.

Old entries without identity still show their outcomes and are labelled Identity not recorded or unavailable. They are not discarded or silently assigned to today's project. Refresh is read-only: it never starts, resumes or retries a job. Choose Refresh again after changing the selected project or settings.

Background builds capture the selected project's absolute root before queuing work. Changing Studio's process directory cannot redirect later phases to another relative project. External file edits are still possible while a build runs; this is not an immutable source snapshot.
