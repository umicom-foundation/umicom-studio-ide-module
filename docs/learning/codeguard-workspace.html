Keep a quality review with its Studio workspace

This lesson is for contributors connecting Studio commands to shared Framework services. The C service API below is implemented in source. The native Tools and Output binding now uses it for saved-source review and cancellation. Both layers require runtime qualification; a menu label or configuration result does not prove an end-to-end workflow.

1. Start with one owner

Studio's service container owns the workspace graph, task queue and quality review. Framework owns scanning, cancellation and retained findings. A thin Studio wrapper supplies the current workspace root and revision. It does not start another thread pool or implement a second scanner.

Call UmiStudioCodeGuardBegin, Poll, Snapshot, Cancel and Result on the thread which created the service container. The creating thread is recorded during construction, before the first scan. A queue worker cannot become the owner merely by requesting the first scan.

2. Accept a request without waiting for it

#include "umicom/studio/codeguard_workflow.h"

uint64_t request = 0;
UmiStatus status = UmiStudioCodeGuardBegin(services, NULL, &request);
if (status == UMI_STATUS_OK) {
    /* Admission succeeded. The event loop can continue handling input. */
}

A NULL profile selects Framework defaults. An explicit profile is copied into the job, so changing a stack variable later cannot change an admitted request. Begin requires an open workspace and captures its absolute root. Changing the process's current directory afterwards does not redirect the job.

A scan reads saved source files and does not execute project commands, so this API allows an open untrusted workspace. This permission does not authorize build, run, install or network actions. Findings also do not include unsaved editor buffers and do not represent an immutable filesystem snapshot.

Only one job may be pending in a review. Before accepting a replacement, Begin polls the previous job and retires it if possible. BUSY means it still owns unfinished work. A failed call leaves the caller's request output unchanged. Request IDs are scoped to a root-bound review; pair them with the workspace context ID rather than treating the number as a global identity.

3. Poll and interpret two outcomes

UmiCodeGuardReviewSnapshot snapshot;
UmiStatus status = UmiStudioCodeGuardPoll(services, &snapshot);
if (status == UMI_STATUS_OK && !snapshot.pending) {
    /* snapshot.operation_status describes file analysis.
     * snapshot.status describes whether this attempt could publish.
     * snapshot.has_report may describe a retained earlier success. */
}

Poll never joins a worker. If it returns an API error, the supplied snapshot remains unchanged. A worker failure normally appears in the snapshot instead. For example, a file budget refusal can leave a previous complete report available. Do not label that retained report as the output of the failed attempt.

Snapshot reads the last poll cache without publishing a result or requesting cancellation. It is suitable for command availability checks which should have no execution effects. It masks a cached report immediately when the current workspace no longer matches. Worker progress becomes current only through Poll.

4. Reject results from a different context

The workspace graph supplies a revision which changes when the project session, trust or project list changes. Closing and reopening the same directory therefore does not restore the old request's authority. Poll compares that revision and the bound root. A mismatch marks a pending attempt stale, requests cooperative cancellation and suppresses publication.

A worker might already have succeeded before the workspace changes. In that case the operation status can still be OK while publication returns INVALID_STATE. This is expected: the computation finished, but it belongs to an older workspace. Result returns NULL for a report whose context is no longer current.

Switching to a different root prepares a new Framework controller after the old job retires. Allocation failure retains the old controller. A successful rebind drops the old root's report, even if a later queue admission fails. Returning to that root creates or reuses a controller according to the current binding; never assume a multi-project report cache exists.

5. Borrow findings deliberately

const UmiCodeGuardResult *report = UmiStudioCodeGuardResult(services);
if (report != NULL) {
    size_t count = umi_codeguard_result_count(report);
    /* Copy any fields needed by a longer-lived presentation model. */
    (void)count;
}

Studio owns the report. Do not free it. Finding pointers survive failed attempts against the same review but expire after a successful replacement, root rebinding or service destruction. A GUI callback can close its window or change context; reacquire the native owner and current report before using them after such callbacks.

6. Cancel before releasing storage

Cancel is cooperative and may be called after the workspace closes. It suppresses an unpolled successful attempt as well as requesting cancellation of running work. It does not release worker storage. With no pending review it is a successful no-op.

UmiStudioServicesStopBackground requests review cancellation before stopping and joining the shared queue. Checked service release destroys the review only after that shutdown succeeds. A cancellation, join or release failure retains the service owner for investigation and retry. StopBackground is a blocking lifecycle operation; use it during controlled shutdown, not as a progress-poll operation in a responsive interface.

7. Qualify the real integration

The native fixture constructs real Studio services in a uniquely owned directory. It disables unrelated automation, creates a saved C source file, and exercises Framework's scanner and task queue. Its data directory is retained for diagnosis. It never removes a caller's existing application state.

  1. Configure the Applications checkout with testing enabled.
  2. Build the focused target using the same Framework source and toolchain.
  3. Run the ordinary cases and, on GNU-compatible linkers, the four injected failure cases.
  4. Keep the exact source revisions and test output with the qualification evidence.
cmake -S . -B build/studio-review -DBUILD_TESTING=ON
cmake --build build/studio-review --target umicom-studio-codeguard-workflow-test
ctest --test-dir build/studio-review -R "^studio\.codeguard_workflow\." --output-on-failure

# GNU/Clang toolchains with linker wrapping:
cmake --build build/studio-review --target umicom-studio-codeguard-workflow-fault-test
ctest --test-dir build/studio-review -R "^studio\.codeguard_workflow_fault\." --output-on-failure

The ordinary suite registers 26 cases, including closed and untrusted workspaces, stale completion, retry, copied profiles, a changed current directory, wrong-thread calls and shutdown. Four fault cases cover controller allocation, failed polling before admission, cancellation failure during shutdown and review-release retry. A supported qualified run should pass all selected cases. These tests have been authored; configuration alone cannot establish that they compile or pass.
