Review saved source from Studio

CodeGuard inspects source files and reports patterns which deserve engineering review. Studio connects its native Tools actions to the shared Framework scanner, background queue and report presenter. This lesson explains the authored workflow and the checks needed to qualify it. The native regression cases have not yet been executed; a menu label or a successful configuration is not a runtime result.

1. Understand what the review reads

Open a workspace containing saved source files. The review reads those files from disk. It does not automatically save editor drafts, build the project, execute its programs or upload its contents. An open untrusted workspace is permitted because this action does not execute project commands. This does not grant permission to build or run that workspace.

A finding is evidence for a person to inspect, not proof of a vulnerability. The scanner does not freeze the filesystem. Files can change between its passes, and unsaved text in an editor can differ from the saved file described by the report.

2. Start a review

  1. Open the intended workspace and save any changes you want included.
  2. Select Tools → CodeGuard, or use Scan saved files in the CodeGuard section of Output.
  3. The existing Output surface opens and its CodeGuard section expands.
  4. The application captures the workspace revision before revealing Output and checks it again before submitting the job.
  5. Read the status and report when the background job finishes.

Only one review may be pending for this service owner. The Scan action is disabled while it owns pending work. A retained button or a second direct command repeats the same check; disabled appearance alone is not an ownership rule.

Revealing a native control can invoke application callbacks. A callback might close Studio, switch projects or collapse the section. The command then refuses submission rather than scanning a different workspace by accident. The implementation retains a weak host identity across those callbacks and compares the captured graph revision and root before calling Begin.

3. Read two separate outcomes

The status distinguishes execution from publication. Execution describes whether analysis completed. Publication describes whether that attempt still belongs to the current workspace. A completed job can become stale before its findings are accepted. A failed later attempt may also leave an earlier complete report available; the presenter calls it a retained report rather than implying the attempt succeeded.

Framework copies a bounded text projection before updating GTK widgets. The widgets do not keep borrowed finding pointers. If the report is too large for the preview, the status says that the preview is unavailable and the view is empty. The service still owns the complete findings. This native panel does not yet provide a report-export chooser.

4. Use Follow, Refresh and Copy

Follow output displays new accepted evidence automatically. Turn it off to inspect the current text without replacement. Refresh displays the latest accepted preview manually. Copy copies the displayed text; it does not start another scan or export the complete service result.

Workspace changes override a paused view: findings from the retired context are cleared. If a text callback changes the workspace while a copied report is being displayed, Studio rechecks the context and clears that report immediately. A later refresh projects the new workspace. Repeated identical evidence leaves text selection intact.

5. Cancel an owned review

  1. Select Tools → Cancel CodeGuard or Cancel review in Output.
  2. The service requests cooperative cancellation. It does not free memory still used by a worker.
  3. Continue handling UI events while the normal refresh retires the job.
  4. Inspect the terminal status before starting another review.

Cancellation remains available for an owned pending job after the workspace closes. Closing or replacing a workspace also causes polling to reject stale publication and request cancellation. A queued attempt can therefore retire before a later explicit Cancel click; at that point no pending operation needs cancellation. Cancellation cannot forcibly interrupt blocking operating-system file access.

6. Follow the ownership boundary in C

UmiCodeGuardReviewSnapshot review;
UmiStatus status = UmiStudioCodeGuardPoll(services, &review);
if (status == UMI_STATUS_OK) {
    const UmiCodeGuardResult *report = review.has_report
        ? UmiStudioCodeGuardResult(services) : NULL;
    status = UmiCodeGuardOutputGtk4Update(panel, context, &review, report);
    /* GTK callbacks may have retired the application. Resolve the weak
     * owner again before reading services or the workspace here. */
}

This fragment illustrates one boundary, not a complete event-loop implementation. All review operations belong to the service container's creating thread. The production native binding also checks current context, handles API failures, prevents nested publication and deduplicates repeated failure notifications.

A polling error clears the previous preview and reports that the update is unavailable. Recovery must invalidate the presenter's equality cache as well as clear the visible text; otherwise an unchanged successful report could remain invisible. The binding publishes an empty shared snapshot, then allows the next successful observation to restore current evidence.

7. Qualify menu and output behavior

The native fixture creates an isolated temporary workspace, real services, a real task queue and native GTK controls. It retains the fixture directory for diagnosis. A controlled queue blocker makes pending-job and text-observer cases deterministic, including on fast machines.

From an Applications checkout configured with GTK4 and testing enabled, use the corresponding build directory:

cmake --build build/windows-ucrt64-all-debug --target umicom-studio-codeguard-native-test
ctest --test-dir build/windows-ucrt64-all-debug -R "^studio\.codeguard_native\." --output-on-failure

# GNU-compatible linker wrapping enables the focused polling failures:
cmake --build build/windows-ucrt64-all-debug --target umicom-studio-codeguard-native-fault-test
ctest --test-dir build/windows-ucrt64-all-debug -R "^studio\.codeguard_native_fault\." --output-on-failure

The ordinary target registers 22 cases. Three additional cases inject a polling failure, verify recovery of unchanged findings and reject old-context text during failure. A machine without a usable GTK display reports a skip, which is missing coverage rather than a pass. Configuration checks target registration; compilation, assertions, callback lifetime and rendered appearance need actual execution.

After the automated checks, exercise the same actions in a qualified Studio build. Confirm the approved logo and Windows icon, keyboard/menu discovery, visible status, paused output, cancellation and project switching. Keep failed and skipped results alongside passes. If a command is unavailable, check for a closed workspace or a pending job; if the preview is unavailable, inspect the underlying operation status before retrying.
