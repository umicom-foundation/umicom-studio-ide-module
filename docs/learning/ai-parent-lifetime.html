Keep AI parents alive through callbacks

A child service can correctly refuse destruction while its parent still frees the memory that child needs. This lesson explains how Studio carries a checked Framework result through two levels of ownership: its AI platform and its application service container. Prerequisites are C pointers, structures, callbacks and return statuses. Read Coding service ownership first.

1. Draw the ownership relationships

Studio's service container owns an AI platform. That platform owns a coding assistant, an AuthorEngine service and an AI runtime. The coding assistant borrows AuthorEngine. A patch operation calls a file adapter supplied by its caller. While that callback runs, both the assistant and its borrowed dependencies must remain alive.

If a callback requests shutdown, returning BUSY from the assistant alone is insufficient. A parent that ignores that result could free AuthorEngine and the runtime. Returning from the callback would then resume code with invalid pointers. No amount of checking a pointer for NULL can prove that its allocation is still alive.

2. Preflight before unrelated shutdown effects

UmiAiCodingAssistantCheckIdle reports whether a patch operation is active. Studio's UmiStudioAiPlatformCheckIdle also checks its own destruction guard and Framework runtime activity and provider ownership. The service container calls this before cancelling or stopping unrelated work. A refusal therefore preserves the aggregate state at this boundary.

An idle check is an observation under serialized access, not a lock or reservation. Another thread must not begin work between the check and destruction. The lifecycle controller remains responsible for excluding all other callers. The checks cover synchronous patch callbacks, Framework generation and teardown reentry. Raw provider calls, arbitrary tool or Helix activity and detached workers still require separate lifecycle control.

3. Retain a handle when release refuses

#include "umicom/studio/services.h"

UmiStatus close_owned_services(UmiStudioServices **owner)
{
    /* The caller has already retired UI aliases and concurrent work. */
    UmiStatus status = UmiStudioServicesRelease(owner);
    if (status != UMI_STATUS_OK) {
        /* Keep *owner for diagnosis and a later lifecycle-controlled retry. */
        return status;
    }
    /* Successful release has cleared *owner. */
    return UMI_STATUS_OK;
}

The direct platform API accepts a pointer rather than pointer-to-pointer. After UmiStudioAiPlatformDestroyChecked(platform) returns OK, its owner must set its handle to NULL. On failure, retain the pointer. Do not retry inside the same active patch callback: return from the callback first and arrange shutdown after the outer operation finishes.

Legacy void destructors remain available. They delegate to the checked implementation and leave a refused owner alive, but cannot report why release failed. New lifecycle code should use the checked APIs. A late shutdown failure may leave a partially stopped service graph, as in the existing checked shutdown contract; preserve it for recovery rather than resuming ordinary commands.

4. Guard destructor callbacks too

Registered AI providers can have their own destroy callbacks. During platform teardown, these callbacks run after dependent AI services have been released. The platform keeps its destruction flag set throughout provider cleanup. The service container similarly guards nested release. Reentrant teardown returns BUSY instead of freeing the same graph twice.

Provider destructors must not use already retired AI children, rewrite the provider registry or start new work. The guard does not turn arbitrary callback behavior into a safe operation. Registry validation also assumes every borrowed identifier still points to readable, stable storage.

7. Carry generation activity through the parent graph

A provider callback can ask the application to close while Framework still holds its instance. Studio's idle preflight now delegates to UmiAiRuntimeCheckIdle as well as checking the coding assistant and its own teardown flag. Framework owns the callback tracking; Studio does not duplicate that mechanism.

The runtime detects synchronous generation through both its legacy and checked generation entry points. Studio platform destruction, service release and background-stop preflight therefore return BUSY before releasing dependent owners. Legacy void destructors retain the same graph. Return from the provider callback normally, then retry shutdown under the lifecycle controller after the outer call finishes.

The parent-lifetime suite adds 24 cases combining six teardown/idle entry points with both generation APIs and provider success/error outcomes. Each case checks retained service storage and child identity during the callback, then successful final cleanup and exactly one provider destruction after it returns. The provider callback is controlled test code; no model process, network request or GUI is launched.

# Focus only on provider-generation callbacks in a configured Applications build.
cmake --build build/windows-ucrt64-all-debug --target umicom-studio-ai-parent-lifetime-test
ctest --test-dir build/windows-ucrt64-all-debug -R '^studio[.]ai[.]parent-lifetime[.]generation[.]' --output-on-failure

This does not cover providers invoked directly through raw function pointers, arbitrary tool or Helix callbacks, or workers running concurrently with shutdown. Retire those callers explicitly before freeing the platform. An idle result is still a current observation, not permission to ignore later activity.

8. Retain parents during health probes

Health refresh can invoke either a registered provider's health callback or an endpoint-specific probe supplied by the caller. AuthorEngine now retains its borrowed runtime throughout the refresh. Studio checks UmiAiAuthorEngineServiceCheckIdle before releasing siblings and propagates the checked AuthorEngine destruction result before clearing that child pointer.

The same lifecycle rule applies: a callback that requests shutdown receives BUSY, keeps the graph alive, returns normally, and lets the lifecycle controller retry later. A probe error or malformed health value still ends the activity scope. Legacy provider callback errors retain their unavailable-health behavior; descriptor-aware probe errors remain explicit failures.

cmake --build build/windows-ucrt64-all-debug --target umicom-studio-ai-parent-lifetime-test
ctest --test-dir build/windows-ucrt64-all-debug -R '^studio[.]ai[.]parent-lifetime[.]health[.]' --output-on-failure

The 54 cases combine both health APIs with success, callback failure and malformed output, across direct AuthorEngine and Studio parent cleanup entry points. Each checks retained parent storage and final single provider destruction. These fixtures do not start a model, access a network endpoint or establish GUI shutdown behavior.
