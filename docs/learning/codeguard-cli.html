Reliable CodeGuard command results

A command has more than one responsibility: it must inspect the requested files, deliver its report and tell the calling shell what happened. This lesson follows Studio's small native CodeGuard command. Framework owns scanning, reports and native argument capture; Studio chooses the command's exit codes.

1. Run the existing positional interface

After building the umicom-studio-codeguard target, run its executable with a workspace directory. The Applications build normally places executables in its bin directory; check the configured output location if that file is absent.

& ".\build\windows-ucrt64-all-debug\bin\umicom-studio-codeguard.exe" "C:\Projects\Example"
$LASTEXITCODE

The argument is a directory, not a command to execute. With no directory argument, the command scans its current working directory. It uses the default quality profile and writes a text report to standard output. Legacy extra positional arguments remain ignored; they are not supported format or export options. Use the shared umicom quality scan command when you need its explicit format and export options.

The scan reads saved files. It does not include unsaved editor text, freeze the filesystem or prove that a reported pattern is exploitable. Inspect a finding in its source context.

2. Distinguish three outcomes

Exit codeMeaningNext step
0Analysis and report output completed; no finding met the default failure threshold.Review lower-severity findings as appropriate.
1Analysis and output completed; at least one finding met the threshold.Review the reported finding and decide the correction.
2Native argument capture or session creation failed.Check the input path and diagnostic, then retry.
3Analysis or report output failed.Resolve the operational error before treating the report as complete.

The default failure threshold is high severity. An output failure takes precedence over that threshold: exit 3 is returned even when the analysis itself found no high-severity issue or would otherwise have returned 1. A destination can contain only part of a report after a write fails. Do not interpret a partial file as a complete clean result.

3. Keep resource cleanup on every owned path

status = umi_studio_codeguard_scan(guard, &profile);
if (status == UMI_STATUS_OK)
    status = umi_codeguard_report_write(stdout, UMI_CODEGUARD_REPORT_TEXT,
        umi_studio_codeguard_result(guard));
UmiCodeGuardSummary summary = umi_studio_codeguard_summary(guard);
umi_studio_codeguard_destroy(guard);
if (status != UMI_STATUS_OK)
    return 3;
return umi_codeguard_summary_failed(&summary, profile.fail_on) ? 1 : 0;

The detailed report is borrowed from the session, so output must finish before destruction. The small summary is copied by value and remains valid afterwards. A failed scan does not fall through to report an empty result. A failed write does not fall through to report a successful severity gate.

The implementation prints operational diagnostics to standard error. If that stream also fails, the exit code still conveys failure. The command does not install a process signal handler: on POSIX, a shell may terminate a process with a broken-pipe signal before a C stream reports an error. The controlled read-only-descriptor tests below exercise a returned write error without changing signal policy.

4. Capture Unicode at the process boundary

On Windows, narrow C runtime arguments can lose characters which the current code page cannot represent. The entry uses Framework's UmiNativeArgumentsDispatch to capture the original Unicode command line and call its UTF-8 callback. Framework owns and releases the copied argument storage. This does not change the console font, output encoding, locale or working directory.

Do not use native capture to reinterpret a synthetic test vector: Windows capture reads the process's actual command line. Callback tests therefore call the internal run function directly. Separate CTest cases launch the real executable with an empty workspace and a workspace whose name contains accented and Japanese characters.

5. Reproduce output failure deliberately

A reliable regression does not depend on filling a real disk. The fixture opens a retained input file read-only, duplicates its descriptor onto standard output, runs the production callback, then restores standard output before checking results. The OS rejects report writes. The fixture checks exit 3 and verifies that the input file was unchanged.

Other cases cover a clean directory, an unsafe-copy finding, default current-directory behavior, UTF-8 paths, missing or empty roots and the compatibility argument convention. GNU-compatible linker wrappers inject session creation, scan, report and native capture failures, and count destruction to verify cleanup. These fault cases are authored tests, not evidence of execution.

cmake --build build/windows-ucrt64-all-debug --target umicom-studio-codeguard umicom-studio-codeguard-cli-test
ctest --test-dir build/windows-ucrt64-all-debug -R "^studio\.codeguard_cli(\.|_process\.)" --output-on-failure

# GNU-compatible linker fault cases:
cmake --build build/windows-ucrt64-all-debug --target umicom-studio-codeguard-cli-fault-test
ctest --test-dir build/windows-ucrt64-all-debug -R "^studio\.codeguard_cli_fault\." --output-on-failure

Run commands separately and stop on errors. Configuration registers tests but does not compile or execute them. A supported linker is required for the injected faults; the ordinary cases remain available without wrapping. The tests retain their temporary workspace paths for diagnosis.
