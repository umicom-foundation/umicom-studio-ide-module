Choose and save a native debugger

A debug adapter lets Studio inspect a running program. Studio supports a GDB build with DAP support or LLDB's lldb-dap adapter. Choosing an adapter does not install it or start your program.

Use an installed adapter

  1. Open the Debug panel and choose GDB (DAP) or LLDB DAP.
  2. Enter the full executable path, such as C:/msys64/ucrt64/bin/gdb.exe, if that is where you installed a compatible adapter. Leave the field empty to use its usual PATH lookup. Do not add command arguments.
  3. Choose Use adapter. Studio copies this choice into the current window. A running or pending debug session must stop before the adapter can change. Reopening the panel shows the accepted choice.
  4. Review your project's program, arguments and working folder in Project Settings. Build with debug symbols, then use Debug. The existing trust and build-success checks still apply.

Keep the choice for later

  1. Review the two adapter fields and choose Save adapter choice locally. The save runs on a worker and reports its full destination path. A nonempty path must be absolute.
  2. Studio stores native-debug-adapter.json in its per-user configuration folder, using Framework's application-path service. It does not save this preference in the opened project's repository.
  3. In a later window, choose Load saved adapter choice. Loading fills the draft fields; it does not change the active adapter. Review them and choose Use adapter separately.

Recover from a problem

If loading fails, check the reported location and keep or correct your current draft. A malformed file, unsupported adapter name or relative executable path is rejected. Saving a valid choice explicitly replaces the local settings file. An existing directory or symbolic-link destination is refused.

If you edit the draft while loading, Studio keeps the newer draft. Loading and saving block another preference action or Use adapter until completion. Closing the window discards a loaded result; an explicit save may finish after closing. Save and load never grant trust or execute the selected adapter.

Preferences record a path, not proof of a working installation. An executable can be moved, lack DAP support or require a different environment. Check the Debug output when a launch fails. File replacement does not coordinate competing Studio windows; the last successful save wins.

Extend the workflow

Framework owns validation, JSON, user paths and local file replacement. Studio owns the visible draft and resolves its window again after asynchronous completion. New adapter types should add explicit validation and protocol support before their names are accepted. Keep load, review and execution as separate actions.
