Compare an editor draft with its saved file

Read both versions of an Umicom Notes source file before deciding which text to keep.

Why there can be two versions

The text in an editor tab is a draft. The file on disk is the saved version. They agree immediately after a successful save, but can become different in either direction. Typing changes the draft; another editor or a Git operation can change the saved version.

Compare with saved lets you inspect those two texts without changing either one. The left pane contains the captured draft and the right pane contains the captured saved text. Both panes are read-only: you can select and copy text, but typing into the review does not edit your project.

Saving and reloading are different decisions. Save writes your draft to the file. Reload replaces the draft with the saved text. Comparing alone performs neither operation.

1. Prepare a Notes project

Use a disposable practice project. In Studio, create a C23 Console Application named Umicom Notes, or open a practice project that already builds. Open src/main.c, replace its contents with the program below, and save it.

#include <stdio.h>

typedef struct Note {
    const char *title;
    int saved;
} Note;

int main(void)
{
    const Note notes[] = {
        {"Account setup checklist", 1},
        {"Window layout decisions", 1},
        {"Release notes", 0}
    };
    const size_t noteCount = sizeof notes / sizeof notes[0];
    size_t savedCount = 0U;
    for (size_t index = 0U; index < noteCount; ++index) {
        if (notes[index].saved) ++savedCount;
    }
    printf("Umicom Notes: %zu of %zu notes saved\n", savedCount, noteCount);
    return 0;
}

A Note groups a title and a saved flag. The array contains three records. The loop counts records whose flag is nonzero. The sizeof expression calculates the number of array elements rather than storing a second, easily forgotten count.

Build and run the program through your configured Studio project. Its output should be:

Umicom Notes: 2 of 3 notes saved

2. Make a draft edit and a separate saved-file edit

In Studio, add this comment above main, but do not save:

/* Keep the summary visible in the Notes status panel. */

Now open the same saved src/main.c in a second text editor. Change the Release notes record from:

{"Release notes", 0}

to:

{"Release notes", 1}

Save that change in the second editor. Your Studio draft now contains the comment but the old flag. The saved file contains the new flag but not your unsaved comment. This is a useful case for comparison because neither version contains everything you might decide to keep.

3. Read the comparison before choosing Reload

Return to the source tab and choose Compare with saved on the editor command bar. Scroll the command bar horizontally if the button is outside the visible area. The existing Reload from disk button opens the same reviewed question.

Check the document name first. The header describes the captured text sizes and incoming encoding and line endings. Then read the left and right panes. Next difference selects the next changed line; Previous difference returns to the earlier one. Navigation stops at the first or last change rather than wrapping.

A line may exist on only one side. The position label says none for the missing side; it does not invent a matching line. The panes keep each source's own line order and scroll independently. They are not padded into a permanently synchronised line grid.

The review refers to captured snapshots, not a continuously updating disk view. To inspect later edits, close this question and request another comparison.

4. Choose what to keep

Start by choosing Cancel. Confirm that the unsaved comment is still present in Studio. Cancelling a comparison does not discard it.

To keep both changes, use a deliberate editing workflow: preserve a separate copy with Save As, or copy the useful text, cancel the review and edit the intended version yourself. This comparison is not an automatic merge and it has no Apply selected change operation.

For the exercise, open the comparison again and choose Reload. This explicitly approves replacing the current draft with the saved file. The comment disappears and the flag becomes 1. Reload does not write the saved file.

Choose the editor command bar's Undo. The previous complete draft, including its comment, should return. Redo reapplies the reloaded text. After Redo, build and run again; the output should be:

Umicom Notes: 3 of 3 notes saved

Undo history is bounded and belongs to the open document. Closing the document or evicting old history can remove that recovery option. Use Save As or version control for an alternate version that must be kept.

5. Recognise a stale review

While a review is open, change the saved file again from the second editor. Returning to the old question and approving Reload should be rejected because that question did not show the newest saved text. The current draft remains available. Request a fresh comparison and review the new content.

The same principle protects the document's identity and draft revision. A question must not silently act on another tab or overwrite text edited after the question was prepared.

Larger files, line endings and unavailable actions

The full-text review accepts up to 8 MiB of decoded UTF-8 text per side. The existing line-alignment engine has a smaller bound: 512 lines per side and 1,023 bytes per line. When that bound is exceeded, the review still shows both complete supported texts, but explains why difference navigation is unavailable. This is not a return to the old small editor-file limit.

The saved file is decoded for editing. CRLF and LF differences and the file's encoding are not displayed as a raw binary comparison. The summary identifies the incoming encoding and line endings; final-newline information helps distinguish texts whose line contents otherwise match.

A missing file cannot supply a saved version. Keep the draft and use Save As to preserve it. An untitled document first needs a saved path. A permission, decoding or size error leaves the draft in place and should be resolved before retrying. Reading from slow storage can still pause this synchronous operation.

Review questions

Which text changes when you press Save, and which changes when you approve Reload? Why is Cancel the default? Why must a comparison be prepared again after another program changes the file? Practise answering these questions using the two Notes versions, not just the button names.
