Edit and build a project in Umicom Studio IDE

A project is a folder containing related source files and build instructions. A document tab represents one open file. Opening several tabs should let you move between files without losing unsaved text. A build translates your source into a program; opening a file alone does not configure a project.

Open and edit several files

  1. Open your project folder, then use Open File or the Explorer to open a source file. The editor should show its contents and a tab with its name.
  2. Type a short change. A dot beside the tab name indicates an unsaved document. Open another file, then select the first tab. Your text and its editing buffer should still be present.
  3. Leave the editor idle briefly and switch again. Background status updates should not replace the tab controls or move keyboard focus away from a focused tab.
  4. When there are more tabs than fit, scroll the tab row horizontally. Long names are shortened visually; the tooltip contains the file path. A narrow window should not require all tabs to fit on one line at once.
  5. Choose Save for the current file. For a new unnamed document, choose its destination first. Save each intended change before judging the output of a compiler or running program.

Configure, build and run

  1. Open the Build surface and choose Project Settings. Review the source folder, build folder, selected target and run program. The run program must refer to the executable produced by this project.
  2. Review the project before granting execution trust. A project may run tools during configuration and compilation. Opening it for reading is a separate operation.
  3. Choose Configure. Read the completed result in Output; successful submission of a task is not a successful configuration.
  4. Choose Build. Wait for completion. If it fails, read Problems and Output, open the reported source location, correct the cause, save, and build again.
  5. Choose Test to run the configured project checks. A skipped test is missing coverage, not a pass.
  6. Choose Run after a successful build. If the program cannot start, inspect its configured path and working directory. Debugging additionally needs a compatible debugger and configuration.

Follow build output explains live and completed output. Save build logs explains how to retain emitted diagnostics.

Capture an editing problem

Use a disposable project containing no credentials or private data. Note the file you selected, what you typed, which tab you selected next, and whether the problem occurred after waiting for a status refresh. Keep the build revision, platform, GTK version and relevant logs with the report. Do not publish your normal workspace or private source in screenshots.

The native qualification scenarios studio.first_use.gtk4.tab-visible-workflow and studio.first_use.gtk4.tab-overflow open an isolated Studio window, edit and save test files, and write tabs-open.png, tabs-switched.png and tabs-saved.png in their unique qualification/first-use-…/umicom-first-use-… folders. Their output prints the full image paths. Images are written at individual checkpoints on a graphical desktop. The visible scenarios retain their fixture folders on both success and failure; a later failure does not erase earlier images. They also attempt workflow-failed.png when an assertion fails while the window is still mapped. A crash or failure before the window appears may leave logs without an image.

The toolchain scenarios studio.first_use.gtk4.visible-build-run and studio.first_use.gtk4.visible-build-repair additionally use mapped Configure, Build and Run controls with a generated C23 project. They retain configured, completed-build and program-output images; the repair case also captures the deliberate compiler rejection. The fixture requires the installed native compiler, CMake and build tool.

These scenarios exercise real GTK widgets, buffers, application commands and files. Their activation signals are not operating-system mouse or keyboard input. Review the images and also try real pointer and keyboard navigation before accepting the interface. A screenshot confirms appearance at one checkpoint; it does not prove every action works.

If a tab becomes inaccessible, retain its unsaved work and record the sequence. Do not delete preferences or source files as a first troubleshooting step. Draft recovery describes explicit local recovery snapshots.
