Review a project and its submodules

Source Control includes a read-only repository review. A submodule is a child Git repository: its parent stores a commit identifier, while the child owns its files.

  1. Open the project's Source Control surface.
  2. Expand Repository and submodule review and check the displayed path.
  3. Select Inspect repository. Use the page buttons to read each group of changed paths.
  4. If a child has modified or untracked files, review and commit those inside the child before recording its new revision in the parent.
  5. Inspect again after repository changes. Select Stop to cancel a pending read.

A failed refresh retains the older observation and reports the failure. The review does not stage files, commit changes, fetch or push. It cannot prove that commits have been published or that builds and tests passed.

The panel currently supports Windows and non-Android Linux GTK builds. It displays up to 50 paths per page within Framework's bounded 4,096-entry observation.

Use the Branches menu without changing the repository

A branch is a name for a line of Git history. Viewing that name is different from checking it out: checkout changes the files selected in the working tree. Studio keeps these two actions separate. Source Control → Branches selects the Branches tab already present in the Source Control pane. It does not create a second branch manager, choose a branch, fetch remote commits or publish changes.

  1. Open a project folder in Studio. A project must be open before the Branches command is available. Viewing the pane does not require marking the project trusted.
  2. Choose Source Control → Branches. The Source Control pane opens and its existing Branches tab becomes selected. If that pane is already open, Studio reuses it.
  3. Read the current branch marker, upstream name and available ahead/behind counts. These fields describe the current stored repository observation; opening the tab does not refresh them.
  4. If the provider has not inspected the repository, use the separate Refresh action when you intend to request an observation. A blank list or unavailable provider is not proof that there are no branches.
  5. Return to the commit-message field. Text you typed but did not submit remains a draft. Opening Branches must not turn that text into a commit.

Keep navigation separate from an operation

The branch list includes an explicit Checkout control. That control invokes the existing source-control service and its checks. The Branches menu never invokes Checkout. A branch name supplied as an argument to the navigation command is rejected rather than interpreted as permission to change history. Similarly, selecting a notebook tab is not equivalent to pressing Refresh, Stage All, Pull or Push.

For example, a new project with repository discovery disabled can still display the Branches pane. The expected result is a visible place to inspect state, with no repository operation recorded. You should not replace an unavailable provider with an optimistic “clean” result. Reenable or configure the real provider through the normal project workflow and inspect its returned diagnostics.

What happens when a callback changes the page?

GTK can run callbacks while selecting a tab. A callback is a function notified about an event, such as the selected page changing. That function can close the window, reorder tabs, remove a page or open another project before the original selection call returns. A non-null widget pointer alone cannot prove that the intended page is still active.

Framework resolves the page containing the branch list, retains its identity during selection, and checks the result afterwards. Reordering the same selected page is accepted. Removing it, moving it to another window, hiding it or selecting a competing page produces cancellation. Studio separately checks that its runtime and project revision are unchanged. It never follows a callback into a replacement project and reports that the old request succeeded.

This is a presentation boundary, not a lock on the repository. Later user actions can still change the selected page or project. The command reports what was accepted when it returned. Physical focus, mouse hit targets and the installed GTK package require native acceptance on the target desktop.

Build and exercise the navigation path

From a configured Applications checkout, build the focused fixture and run its tests. Stop if compilation fails; an older executable cannot validate newly edited source. These commands are examples for the normal Windows checkout and do not execute from this page.

Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
cmake --build build/windows-ucrt64-all-debug --target umicom-studio-branch-menu-test
ctest --test-dir build/windows-ucrt64-all-debug -R "^studio[.]source_control[.]branches[.]gtk4[.]" --output-on-failure --no-tests=error

The fixture registers twelve scenarios. They cover actual menu signal dispatch, direct invocation, repeated opening, unexpected arguments, missing or closed projects, retained buttons after teardown, and callbacks that close the host, close the project, reenter, redirect selection or remove the page. The tests use a temporary untrusted project with discovery disabled and compare source-control operation counts and draft text. Registration during configuration is not a passing test result; a skipped graphical test is recorded separately from a pass.

  1. Use the physical mouse to open the Source Control menu and choose Branches. Confirm the existing page is visible.
  2. Type a draft commit message, visit Branches twice and return. Confirm the exact text is unchanged and nothing was committed.
  3. Close the project. Confirm the Branches command becomes unavailable. Open a different project and confirm observations refer to that project.
  4. If a command is refused, inspect the project and provider state. If it is cancelled, check whether a callback closed or replaced its intended destination before retrying from the current window.

Developers can follow the same ownership rule in other products through Framework’s notebook-selection API. Keep project policy in the application and native widget lifetime in the shared adapter.

Learn the shared native ownership contract

Why an old Checkout button must lose authority

A displayed branch row belongs to one observation in one project. After a refresh replaces that row, a program may still retain the old button object for accessibility or testing. Retaining memory does not keep its authority to change the current repository. The same applies when Studio closes its workbench or the user changes projects.

Studio creates Checkout controls through one native factory. Each control uses the existing weak runtime binding and captures the project root and revision. On activation, the callback verifies that its owner is still current, the button is sensitive, it still belongs to the current branch list, and the project identity is unchanged. Only then does it copy the branch name and call the registered source-control command. The registered command still owns the operation and its own availability checks.

Copying the name matters even during a synchronous call. The command can refresh the list or report an outcome that closes the window before returning. That can destroy the original row and its associated string. The callback keeps an owned copy across execution and never reads the old runtime afterwards. The original callback and signal wiring remain disabled in the source for engineering comparison.

  1. Keep the current branch button disabled. Emitting its clicked signal directly in a test must still cause no dispatch.
  2. Retain a row, replace the displayed branch list, then emit the retained button. It must cause no dispatch into the new list.
  3. Change or close the project while retaining a button. The captured root/revision must fail admission.
  4. Use a current enabled row and a synthetic registered command. Confirm exactly one call with the displayed branch name.
  5. Make that synthetic command close Studio while returning. Confirm that callback completion does not access the retired runtime.
cmake --build build/windows-ucrt64-all-debug --target umicom-studio-branch-menu-test
ctest --test-dir build/windows-ucrt64-all-debug -R "^studio[.]source_control[.]checkout[.]gtk4[.]" --output-on-failure --no-tests=error

These ten scenarios include the production workbench implementation so they exercise the actual private button factory and signal callback. The fixture replaces only the final registered checkout handler with a counter. It does not invoke Git or establish that a real checkout preserves local changes; repository-operation qualification remains separate. A configured test name is not an executed result.
