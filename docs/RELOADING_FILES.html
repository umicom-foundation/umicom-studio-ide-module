Reloading saved files without losing track of your work

An open document and its saved file are two different things. Studio holds your current text in memory. The saved file holds the version last written to disk. Another editor, a Git update or a code generator can change that file while your tab is still open.

Save writes your draft to the file. Reload from disk reads the file into your draft. Choosing the wrong direction can discard the version you meant to keep. This lesson shows how to inspect the situation, keep your work and deliberately choose the version to use.

1. Prepare a Notes project

Use a disposable project rather than an application you depend on. In a built copy of Studio, create an Umicom Notes C23 Console Application. Open src/main.c, enter the following source and save it. Build and run it once before testing reload.

#include <stdio.h>

typedef struct Note {
    const char *title;
    int saved;
} Note;

static unsigned CountSavedNotes(const Note *notes, size_t count)
{
    unsigned savedCount = 0U;
    for (size_t index = 0U; index < count; ++index) {
        if (notes[index].saved) ++savedCount;
    }
    return savedCount;
}

int main(void)
{
    const Note notes[] = {
        {"Project ideas", 1},
        {"Meeting notes", 1},
        {"Release checklist", 0}
    };
    const size_t count = sizeof notes / sizeof notes[0];
    printf("Umicom Notes: %u of %zu notes saved\n",
        CountSavedNotes(notes, count), count);
    return 0;
}

The Note structure keeps a title and a saved flag together. CountSavedNotes inspects the array without changing it. The count calculation divides the size of the entire array by the size of one element, so it remains correct if you add another note.

The program should display Umicom Notes: 2 of 3 notes saved. It is a small status report for this exercise, not a file-saving service. The flag belongs to our sample program; it is separate from Studio's own unsaved-document indicator.

2. Change the saved file outside Studio

Leave the source tab open. Use another text editor to open the same src/main.c. Change the last record from {"Release checklist", 0} to {"Release checklist", 1} and save it there.

Return to Studio. Your tab can still show the previous text: reading a file when it first opens does not continuously replace the draft. Press External? on the editor bar to check the saved version. A detected change appears in the document information as saved file changed.

Choose Reload from disk on that bar. The question names the document and reports the previous and incoming text sizes. Review the name before accepting. Choose Reload to use the saved version, or Cancel to leave the tab as it is. Cancel is the default button.

After accepting, the tab should contain the flag value 1. Build and run again. The program should now display Umicom Notes: 3 of 3 notes saved. Reload did not compile the code; building remains a separate step.

3. Reload when your tab contains new work

In Studio, add a comment to the source but do not save. For example, write /* Review the release checklist before publishing. */ above the array. The tab now contains an unsaved draft, even though the saved file is still valid C.

Press Reload from disk again. This time the question warns that the operation will replace unsaved text. Choose Cancel first. Confirm that your comment remains in the tab. Preparing and cancelling the question must not save, erase or modify it.

To keep both versions, cancel and use Save As to put the draft in a separate file before proceeding. Choose a new destination, and review any existing-file warning. Do not assume that a similarly named tab is the same document.

For this disposable exercise, request Reload again and approve replacing the draft. The comment should disappear because it was never in the saved file. Use the editor bar's Undo operation once. The previous complete draft, including your comment, should return. Its restored text is unsaved; Undo does not rewrite the disk file.

Undo history belongs to the open document and has size and entry limits. Closing the document, ending the application or making enough later edits can release older history. It is a convenience, not a durable backup or a promise of crash recovery. Save an important alternate version before replacing it.

4. Understand a stale reload question

A reload question applies to one document and one reviewed version. It does not mean “reload whichever tab is active when I click”. Framework captures the document's identity, path, saved revision and draft revision.

If the draft is edited or saved, the file is renamed through Save As, the document is closed, or the saved file changes again before acceptance, the older plan is rejected. Request Reload again to review the new situation. The operation does not silently convert an earlier approval into permission to discard newer work.

The native question is modal, so you cannot normally switch tabs through the same window while it is open. Another process can still update the saved file. Other frontends may provide a non-modal question; they use the same document-specific Framework checks.

5. Handle a missing or unreadable file

When a saved file is deleted, its existing draft can still be useful. External? reports that the saved file is missing. Reload cannot recover bytes that are no longer there. Keep the tab open and use Save As to preserve the text at a reviewed destination.

A permission failure is different from deletion. Check the account's access to the file or reconnect its storage, then retry. Studio must not label an unreadable file as deleted merely because reading failed.

If another editor restores the original contents, run External? again. A conclusive comparison can clear the old changed-file indication. An unsuccessful check does not prove that the external change has disappeared.

6. Text encodings and read-only tabs

Reload uses Framework's existing text loader. It checks supported encoding and size before replacing the draft. UTF-16 with a supported byte-order mark is decoded for editing; the detected encoding and line-ending choice are retained for subsequent saving. Mixed line endings use the existing normalisation policy rather than preserving every line's original spelling.

A clean read-only tab can refresh its displayed text. A read-only tab that already contains an unsaved draft is not replaced by this operation. Clear the reason for the read-only state through the appropriate application control rather than forcing a reload.

The current reload path accepts at most 8 MiB of raw input and 8 MiB of decoded UTF-8 text. A short UTF-16 input can expand during decoding, so both bounds matter. Binary or invalid text is rejected before it can replace the document.

7. A useful everyday routine

Before receiving source updates through Git, save or deliberately preserve your local work. After the update, use External? and Reload for the documents whose saved files changed. Explorer Refresh updates the file list; it does not reload each editor draft. Find in Files searches saved files; its results may differ from text that exists only in an unsaved tab.

These checks are requested by the user. This workflow does not automatically monitor every tab or merge two competing versions. Reload and the external check currently read on the document owner thread; slow storage can delay the interface. Use local disposable files for the first acceptance exercise.

How the controls connect to Framework

The editor bar is composed in applications/studio/src/gui/workbench/runtime/interaction/editor_controls.inc. The confirmation presenter owns a prepared reload plan until you answer or dismiss it. The shared operation is implemented in framework/src/document/coordinator.c, with its public contract in framework/include/umicom/document/coordinator.h.

The registered Framework command umicom.document.revert is named Reload from Disk. Direct command callers may reload a clean document only; unsaved text requires the prepared-plan approval flow. Passing a force argument is not a substitute for approval.
