Inspect Studio services

The native Studio state tool reports the Framework services available to a Studio process. A service is a shared object used by application components, such as a document store or task queue. The tool starts its own composition. It does not attach to an already running IDE, inspect another user's session, or prove that a GUI workflow works.

Show the operational summary

  1. Build the umicom-studio-state target using your configured Applications build.
  2. Open PowerShell in the directory whose Studio state you want to inspect. Startup can create normal local Studio session files there.
  3. Add the UCRT64 runtime directory to the process path and run the tool.
Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
& ".\build\windows-ucrt64-all-debug\bin\umicom-studio-state.exe"

The existing summary includes counts of modules, services, commands, documents and other operational state. It observes this process; it is not a transaction covering every subsystem at one instant.

List service providers

New-Item -ItemType Directory -Force "C:\umicom\_local\logs\studio-services"
& "C:\umicom\Umicom-Applications\build\windows-ucrt64-all-debug\bin\umicom-studio-state.exe" --services 2>&1 | Tee-Object "C:\umicom\_local\logs\studio-services\inventory.log"

The report begins with Registered services: and a count. Each row contains a service identifier, provider identifier, three-part version and hexadecimal flags. Diagnostic messages also use the error stream, which the command above saves in the same log.

ValueMeaning
0x1One provider is permitted for that service identifier.
0x2The registry owns the service's destruction responsibility.
0x4The provider declares the service object thread-safe.
0x8The existing registration permits replacement.

A combined value such as 0x3 means singleton plus owned. These are registration policies, not proof of health or correct implementation. Consult the operational summary and service diagnostics too. Control characters in identifiers are printed as hexadecimal escape sequences to keep each record on one line.

List and filter commands

A command is a named action, such as saving documents or reporting tasks. Discovery copies its description; it does not execute the action or call its enablement callback. Normal Studio startup still takes place.

& "C:\umicom\Umicom-Applications\build\windows-ucrt64-all-debug\bin\umicom-studio-state.exe" --commands
& "C:\umicom\Umicom-Applications\build\windows-ucrt64-all-debug\bin\umicom-studio-state.exe" --commands "studio."

The first form lists every registered command. The second selects identifiers beginning with studio.; this is a case-sensitive prefix, not a wildcard or search in the title. A prefix with no matches produces a successful empty report. Each row contains the identifier, title, category and policy flags.

Command flagMeaning
0x1The command declares that it changes state.
0x2The command declares background work.
0x4The command declares an audit requirement.
0x8The command requires a trusted context.

A declaration is not a permission grant or a health check. An action can be registered yet unavailable in the current context. Review the command's contract before using --execute. Service flags and command flags describe different policies even when their numeric values happen to match.

Framework supplies umi_command_registry_find_prefix for copied rows and UmiCommandRegistryCopySummary for allocation-free policy totals. Both observe one command registry while it is locked. Reports combining several registries do not become one cross-registry transaction.

Understand why reports use copies

A borrowed registry descriptor points into registry-owned storage. Removing or replacing an entry can invalidate it. Studio asks Framework to copy metadata into its own array instead. The array contains no service object addresses or destructor pointers. It remains readable until the tool frees it, even if the registry changes after capture.

The public API is UmiServiceRegistryCopySnapshots. Studio's UmiStudioStateCopyServices wrapper supplies the bootstrap's registry. Other applications can use Framework's operation without copying Studio logic.

Investigate a problem

  1. If the executable is missing, build the state target in the same configured tree as Studio. Do not mix a newer executable with unrelated older runtime files.
  2. If discovery reports an error, keep its exact status and startup diagnostics. An empty report after failed startup is not a healthy running IDE.
  3. If a provider is unexpected, compare its identifier with the module and service descriptors. Do not infer health from its name.
  4. A cleanup error produces a nonzero exit status and a retained-owner message. Keep the log and investigate the failed phase. Printing an inventory does not prove that shutdown succeeded.

The existing --execute <command-id> [argument] interface remains available. It can change application state; request only intended commands. --services reports registered metadata after normal startup.

For focused qualification, build umicom-studio-service-discovery-test and umicom-studio-state, then select ^studio[.]services[.]discovery[.] in CTest. Cases use separate working directories and include a console check comparing the count with printed rows. Collect compiler and runtime evidence before treating a new build as verified.

The companion CTest selection ^studio[.]commands[.]discovery[.] checks complete, filtered and empty command inventories. It uses the same state executable and compares the reported count with the physical output rows.
