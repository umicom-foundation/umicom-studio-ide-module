Inspect memory in Studio

The Run and Debug workspace can show the bytes behind a variable when your native debug adapter supports memory reads. Each result is a capture taken when you choose Read memory. The view does not change your source files or write to the paused program.

Read your first capture

  1. Open your project, configure its native debugger, and stop at a breakpoint. Select the thread and stack frame you want to investigate.
  2. In the Variables area, choose Inspect scope. Expand an object with Inspect children if needed. These explicit reads retain the adapter's memory references.
  3. Find a variable with a Memory bytes section. Not every adapter or variable exposes a memory reference. The initial compatibility root rows do not contain one.
  4. Enter a signed decimal byte offset. Start with 0. Set the number of bytes from 1 to 4096; the default is 256.
  5. Choose Read memory. The adapter may take up to 1.5 seconds to respond. Changing the fields alone sends no request.
  6. Read or select the report text. It shows the returned address, requested range, actual byte count, hexadecimal bytes and printable ASCII characters. Row offsets start at the returned address. Dots stand for non-printable bytes.

Read another range

Change the offset or count and choose Read memory again while the same stop remains selected. Negative offsets are allowed. Offsets must be whole decimal numbers between -9007199254740991 and 9007199254740991; spaces, hexadecimal input and trailing text are refused. The report always records the range that produced it, so an edited input does not relabel an earlier capture.

A short result can mean the end of readable memory. Unreadable bytes are reported separately and are not rendered as zeroes. Studio does not automatically request further pages.

Recover from a failed read

If Read memory is unavailable, check that your installed adapter supports it. If the Memory bytes section is absent, inspect the scope or children again and select a variable for which the adapter provides a memory reference. Studio does not invent an address from the displayed value.

If the frame, session or captured variables changed, inspect the current scope again before reading. A failed read retains the earlier output with an explanatory status. That output is historical, not proof of the program's current bytes. Continuing execution or refreshing debugger detail rows removes the old variable controls.

The report is shown locally and is not automatically saved, uploaded or sent to an AI provider. It is a byte view, not a typed-value editor, disassembler or memory writer. Framework owns the protocol and lifetime checks so other Umicom applications can reuse the same inspection behavior.
