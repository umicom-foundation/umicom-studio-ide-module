Saved test reports in Studio

Use the Test Explorer’s Open a saved CTest report section to review a previous test run. This review is separate from Studio’s live test execution and archive controls. You can open a saved report without opening a project.

  1. Finish the build, then create XML and a console log with CTest from your build directory: 
    ctest --output-on-failure --no-tests=error --output-junit "C:/work/private/tests.xml" --output-log "C:/work/private/tests.log"
    Use an existing private folder and keep both files.
  2. Expand the saved-report section in Test Explorer. Choose the XML filename and click Open report. The panel reads it in the background.
  3. Review the captured filename, full report counts, and the default non-passed results. Not run, disabled, skipped and timed out remain separate from failed and passed.
  4. Enter part of a test name, choose an outcome or sort order, and click Apply filters. Name matching ignores ASCII letter case. Next and Previous retain that selection until you apply another.
  5. Use Copy page to copy the current 64-record page. Use Close report to discard the loaded view without deleting its file.

Cancel load prevents a pending read from displaying results. It waits for the local read to finish releasing resources. Closing or hiding the panel also prevents late publication. A later load is a new operation.

A saved report is historical evidence. Studio does not claim it matches the current project, source revision or executables. The original console log is still needed for complete failure details. This panel neither reruns failed tests nor changes the live test selection.

If the report cannot be opened, check the absolute filename, complete JUnit XML format, encoding and 64 MiB size limit. A console transcript is not JUnit XML. If a filter is rejected, the status explains that it was not applied and the previously accepted page stays visible. Correct the draft and Apply again. Missing or malformed replacement files and cancelled loads also retain the accepted report and its captured filename. Path and filter choices are captured together when Open report is selected; later edits require another explicit action.

Review required coverage across hosts

Expand Review required host coverage in Test Explorer to compare saved observations against explicit requirements. This is separate from browsing one report and from running the project's tests. A pass on one host does not replace a required result on another.

  1. Put the complete JUnit reports in a private evidence directory. Create a UTF-8 CSV plan beside them using this exact header and seven fields per record. Replace the illustrative names and source fingerprint with those recorded for your runs: 
    kind,host,configuration,source_identity,test,capability,report
host,desktop,Debug,source-fingerprint-from-the-run,,,desktop.xml
require,desktop,Debug,,notes.open,GTK display,
require,linux,Debug,,filesystem.exchange,Linux filesystem,
    The first row declares a report. Each require row lists an exact test, host and configuration. This example's Linux requirement remains missing host until a corresponding host report is supplied.
  2. Choose the absolute CSV filename. Enter the source/build fingerprint to review, then click Open coverage.
  3. Read the requested identity, counts and each outstanding row. Skipped, disabled, not run, failed, timed out, missing and source-mismatched observations are distinct. No source identity or host capability is independently verified by this panel.
  4. Use Next and Previous for 64-record pages. Copy page includes the current page's identity and scope. Close review clears the view without deleting files.

Changing an entry does not change the accepted review until another Open coverage succeeds. Cancelling, hiding the panel or failing to read a replacement retains the last accepted review. In-progress file reads finish before releasing their resources. Empty plans never establish passing coverage.

CSV plans are limited to 4 MiB and 256 host reports; all report input together is limited to 64 MiB. Use relative report paths beneath a trusted evidence directory. Extra columns, duplicate host/configuration pairs, duplicate requirements, parent traversal and malformed input are refused. Correct the draft and open it again. External evidence never changes the live runner's discovery, selection or results.

Compare saved test runs

  1. Expand Compare two saved test runs in Test Explorer. This feature is available independently of a loaded project.
  2. Select two completed CTest JUnit files: the older baseline and the current report. Use different absolute filenames and keep each run's source revision and console log beside it.
  3. Select Compare reports. The accepted filenames identify the displayed pair. Editing either filename alone does not change that pair.
  4. Review recovered, regressed, added, removed and other changed outcomes. A removed failure has not been fixed. Unchanged outcomes can include continuing failures, so also open the current file under Open a saved CTest report.
  5. Use Next and Previous for 64-record pages. Copy page copies only the displayed page and summary. Close comparison clears the review without changing either file.

A failed or cancelled replacement keeps the accepted pair and page. Cancel load prevents a pending result from being accepted; local reads finish before resources are released. Completed publication keeps text and filename labels together. Read errors usually mean an incomplete run, a wrong filename, an unsupported report format or a file exceeding the 64 MiB per-file limit.

The comparison uses exact decoded test names and saved outcomes. It does not compare source code, verify timestamps, rerun tests, prove a repair, or change Studio's current test discovery, selection and execution results. Empty reports and unchanged failures are not successful qualification.
