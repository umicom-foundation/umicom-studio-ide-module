Run and debug with program arguments

An argument is an input given to a program when it starts. For example, an application might accept a file name and a display mode. Studio keeps those inputs in the project's build profile so Run and Debug receive the same argument boundaries.

Set up a launch

  1. Open the project folder in Studio and save your source changes.
  2. Open the Build panel and choose Project Settings. Check the project folder, build folder and the program to run. The program path is relative to the project folder unless you enter a full path.
  3. For several arguments, clear Program argument (one argument; no shell expansion). Enter the list in Argument list. Use only one of these fields.
  4. For a program which supports these example options, enter:
    --file "notes for review.txt" --mode preview ""
    The program receives five arguments: --file, notes for review.txt, --mode, preview, and an empty value. These are sample inputs; they do not add options to a program that does not already support them.
  5. Review the project trust choice and choose Apply Settings. An unmatched quote or two filled argument fields keeps the form open with an explanation. No partial profile is applied.
  6. Choose Run. The existing project workflow configures and builds the project before launching the selected program. Inspect its output and diagnostics when a step fails.
  7. To debug the same program, choose the installed GDB or LLDB adapter through Studio's debugger controls and start debugging. The same resolved arguments are sent through the Debug Adapter Protocol. Debug still requires an installed compatible adapter, an existing executable and the project's execution permission.

Quotes, empty values and Windows paths

Spaces separate arguments. Single or double quotes keep spaces inside a value. An empty pair of quotes passes an empty argument. A backslash escapes a quote, another backslash or whitespace. Other backslashes remain literal.

--folder "C:\\Work\\Notes with spaces\\"
--title "Sam's notes"
--label "A \"quoted\" value"

These are separate examples. There is no shell expansion: $HOME, %TEMP%, *, semicolons and command-substitution text remain ordinary program input. Enter complete paths when a program needs them.

Older settings and reopening

The original single-argument field remains available. Its entire contents are one literal argument, even when they contain spaces or quote characters. An older saved profile keeps that interpretation. To adopt a list, move the intended values into the new field and clear the original field explicitly.

Settings are saved through Framework's existing project profile store. Save conflicts and corrupt records are reported instead of silently replacing your inputs. Saving settings does not restore a trust decision or start the program. Older executables which do not understand the expanded stored profile may refuse it; use matching Framework and Studio builds.

Argument settings rejectedFill only one argument field, close all quotes and shorten inputs that exceed the limits.
Program not foundCheck the executable path and the build result. Studio does not guess which binary to run.
Debug reports capacity exceededThe lossless quoted argument representation must fit the debugger's 1,024-byte launch record, including its terminator. Escaping can increase its length. Shorten the list; it is never truncated.
Run and Debug both refuse an inputThe argument-list field holds up to 1,023 bytes. It accepts up to 32 values, each at most 511 bytes. UTF-8 characters can occupy several bytes.

This workflow changes launch configuration and serialization. It does not install a compiler or debugger, and source review alone does not demonstrate that a particular installed toolchain can run the project.

Programs that use relative data files

Project Settings also has a Program working folder field. A blank field uses the project root; a relative folder is resolved from that root. Run and native Debug share the selected folder while keeping the executable path relative to the project. See project presets and working folders for examples and recovery steps.

Review environment settings before a launch

A program can also read named environment values. In Project Settings, enter COURSE=practice "DATA_FOLDER=C:/Work/Sample data" in the Run / Debug environment field. These are literal values, not shell commands. Use settings for your own program; Studio does not add support for these names to an application.

  1. Enter the tools folder if your program or debugger needs its programs and libraries. Use a full native directory path.
  2. Choose Review launch settings. The description lists the program, working folder, arguments, override names and tools-folder policy. Environment values remain hidden in this description.
  3. If you edit the environment or tools folder, review again. The old description is marked as changed.
  4. Choose Apply Settings to save the profile, then use Run or Debug. Reviewing alone neither saves the form nor starts a process.

The environment list accepts up to sixteen distinct portable names in 1,023 UTF-8 bytes. Names start with a letter or underscore, followed by letters, digits or underscores. Quote values containing spaces; duplicate names, including different capitalisation, are refused. An empty value overrides a variable with an empty string. Other host variables remain inherited.

If review fails, check the environment syntax and tools path as well as the launch fields. The review does not check whether files, toolchains or debuggers are installed. Saved profiles contain these values as ordinary configuration; this field is not a password or API-key vault.

Check the program and working folder

  1. In Project Settings, enter the program and working folder you intend to use. An explicit path such as ./build/my-program.exe resolves from the project folder.
  2. Choose Check launch files. A background check reports each resolved path, its filesystem status and whether it has the expected type: a regular file for the program, or a directory for the working folder. Nothing is launched or saved.
  3. If a file is missing, check the build result and correct its location. If a directory was entered as the program, select the executable inside it. A symbolic link or reparse point is reported as such; this check does not follow it to approve a program.
  4. If you change launch inputs while checking, the result is marked out of date. Run the check again, review arguments and environment settings, then apply the settings separately.

A bare name such as my-program is not searched through PATH by this check. Run may resolve that name through operating-system lookup, while native Debug uses the project-relative file shown separately. Use an explicit file path for a consistent choice.

A file having the expected type does not verify executable permissions, architecture, required libraries or debugger compatibility. Files can change after the check. Closing the form requests cancellation; an operating-system metadata call already in progress may finish later.

Run a program that you have already built

  1. Open your project and review its Project Settings. Enable build tools only for a project you trust.
  2. Set Program to run to the executable you intend to use, such as ./build/my-program.exe. Use an explicit path rather than a bare program name. Select an existing Program working folder, or leave it blank to use the project folder.
  3. Apply the settings. Choose Run current executable from the Run menu or command search. This action starts the selected existing file without saving or rebuilding your source. Unsaved edits will not be present in that executable.
  4. Read Output for the result. A queued message means the request was accepted; it does not mean the program started or finished successfully. Use the normal Stop action if the program needs to be cancelled.

A file can exist yet fail to run because its required libraries, permissions or architecture do not match the machine. Files may also change after inspection. The native launcher reports those failures in Output. If you want to compile your current edits first, use Build and run project instead.

Keep build settings with their project

Build, Run, Debug and queued build operations check that their source folder is still the project you opened. Trusting one project does not authorize a profile that points to another project.

  1. If Studio says the build profile no longer matches the open project, save your work and use Open Project to select the intended source folder.
  2. Review its source folder, build folder, configuration and program in Project Build Settings. An absolute source folder identifies the project independently of where Studio was launched.
  3. Enable the project's build tools only after reviewing that project. If a build or debugger is already active, wait for it or use Stop before starting another operation.
  4. Retry the command and read Output for its actual result.

A rejected command leaves the build profile and operation history unchanged. It does not silently substitute another project, enable trust or begin a compiler or debugger process.
