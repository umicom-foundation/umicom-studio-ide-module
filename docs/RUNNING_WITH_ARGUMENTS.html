Run and debug with program arguments

An argument is an input given to a program when it starts. For example, an application might accept a file name and a display mode. Studio keeps those inputs in the project's build profile so Run and Debug receive the same argument boundaries.

Set up a launch

  1. Open the project folder in Studio and save your source changes.
  2. Open the Build panel and choose Project Settings. Check the project folder, build folder and the program to run. The program path is relative to the project folder unless you enter a full path.
  3. For several arguments, clear Program argument (one argument; no shell expansion). Enter the list in Argument list. Use only one of these fields.
  4. For a program which supports these example options, enter:
    --file "notes for review.txt" --mode preview ""
    The program receives five arguments: --file, notes for review.txt, --mode, preview, and an empty value. These are sample inputs; they do not add options to a program that does not already support them.
  5. Review the project trust choice and choose Apply Settings. An unmatched quote or two filled argument fields keeps the form open with an explanation. No partial profile is applied.
  6. Choose Run. The existing project workflow configures and builds the project before launching the selected program. Inspect its output and diagnostics when a step fails.
  7. To debug the same program, choose the installed GDB or LLDB adapter through Studio's debugger controls and start debugging. The same resolved arguments are sent through the Debug Adapter Protocol. Debug still requires an installed compatible adapter, an existing executable and the project's execution permission.

Quotes, empty values and Windows paths

Spaces separate arguments. Single or double quotes keep spaces inside a value. An empty pair of quotes passes an empty argument. A backslash escapes a quote, another backslash or whitespace. Other backslashes remain literal.

--folder "C:\\Work\\Notes with spaces\\"
--title "Sam's notes"
--label "A \"quoted\" value"

These are separate examples. There is no shell expansion: $HOME, %TEMP%, *, semicolons and command-substitution text remain ordinary program input. Enter complete paths when a program needs them.

Older settings and reopening

The original single-argument field remains available. Its entire contents are one literal argument, even when they contain spaces or quote characters. An older saved profile keeps that interpretation. To adopt a list, move the intended values into the new field and clear the original field explicitly.

Settings are saved through Framework's existing project profile store. Save conflicts and corrupt records are reported instead of silently replacing your inputs. Saving settings does not restore a trust decision or start the program. Older executables which do not understand the expanded stored profile may refuse it; use matching Framework and Studio builds.

When a launch is refused

What you seeWhat to check
Argument settings rejectedFill only one argument field, close all quotes and shorten inputs that exceed the limits.
Program not foundCheck the executable path and the build result. Studio does not guess which binary to run.
Debug reports capacity exceededThe lossless quoted argument representation must fit the debugger's 1,024-byte launch record, including its terminator. Escaping can increase its length. Shorten the list; it is never truncated.
Run and Debug both refuse an inputThe argument-list field holds up to 1,023 bytes. It accepts up to 32 values, each at most 511 bytes. UTF-8 characters can occupy several bytes.

This workflow changes launch configuration and serialization. It does not install a compiler or debugger, and source review alone does not demonstrate that a particular installed toolchain can run the project.

Programs that use relative data files

Project Settings also has a Program working folder field. A blank field uses the project root; a relative folder is resolved from that root. Run and native Debug share the selected folder while keeping the executable path relative to the project. See project presets and working folders for examples and recovery steps.
