Browse Problems pages in Studio

The workspace Problems pane keeps compiler and runtime diagnostics in a shared Framework model. A page is a group of up to 300 matching records. Paging changes which records are displayed; it does not run a build or change a diagnostic.

  1. Open Problems after a configure or build command reports messages. Read the summary to distinguish matching records from the model's active and resolved totals.
  2. Read the page range below the filters. For example, Page 2 of 4 — rows 301–600 of 907 matching describes the current filtered list.
  3. Choose Next page or Previous page to browse later or earlier results. A disabled button marks a boundary. The source-navigation buttons named Next and Previous remain separate actions.
  4. Type a filter, change severity or sort order, or toggle Resolved. Studio restarts the new query on page one. Matching counts change with the filter; active and severity totals still describe the complete retained model.
  5. Select a row and choose Open, or activate it, to open its source. A row on a later page works like one on the first page. Existing unsaved text for that source stays in its document.
  6. Use Clear only when you want to remove retained records. Clearing the view does not repair the source; another build may report the same problem.

When results change

A page is a snapshot. New compiler messages can change its order and page count. If results shrink, Studio moves an obsolete page position to the last remaining page. An empty query shows No matching diagnostics and disables both page buttons.

If a page button refers to an older model revision, the first click refreshes the evidence and keeps the current position where possible. Review the new range and click again to move. Changing pages clears the row selection; an unchanged refresh keeps it. Filter changes retain a selection only if the same diagnostic is present on the new first page.

Native notifications can interrupt a refresh by closing the window or changing its query. Partial or old rows cannot open a source until a complete current page is available. The next refresh retries the current query. Invalid display encoding appears as replacement characters; original diagnostic bytes and file identities remain in the Framework model.

Limits and troubleshooting

Pages cover the records still retained by the diagnostic model, not an unlimited history. Keep the complete build log when investigating older messages that may have been evicted. A source-less or unavailable diagnostic produces feedback instead of opening a guessed file. An empty Problems list is not proof that a build or test succeeded.

If page controls are missing, confirm you launched the rebuilt Studio executable. If a source cannot open, check the diagnostic path and the build log. Use the source diagnostics guide for the separate language-server inspection workflow.
