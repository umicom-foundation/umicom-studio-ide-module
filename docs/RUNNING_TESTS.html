Running and stopping tests in Umicom Studio

Use Test Explorer to discover a trusted project, run a selection, inspect outcomes and stop a long test without losing completed results.

1. Open a configured project2. Discover the tests3. Run a selection4. Stop a long-running test5. Read results and output6. Practise with Umicom Notes7. Handle changed projects and full history

1. Open a configured project

Open the project in Studio and select its build profile. The profile identifies its source directory, build directory and configuration, such as Debug. Configure and build the project before running its tests. Configuration writes CTest's catalogue; building creates the executable files those tests need.

Trust only projects whose test scripts you are prepared to execute. Test Explorer uses the active trusted workspace and build profile when starting a run. The same project must still be active when its results are applied.

2. Discover the tests

Open Test Explorer and choose Discover. Discovery reads the CTest catalogue without running the test bodies. The window remains available while discovery is pending. Wait for it to finish before starting a run.

The search box filters test names, labels and identifiers. A label is a category stored with a test, such as notes or index. A disabled entry is still useful information, but it must not be counted as a passing test.

3. Run a selection

Use a test's run action or the Run Selected Test command for a small selection. Run All prepares the current run plan, and Failed selects previously failed tests for another attempt. The repeated-selection command runs the same selection more than once.

Starting the operation queues a Framework job rather than waiting for CTest in the window's input handler. The progress line identifies the active test and completed attempt counts. Completed results appear as Studio polls the job, with a bounded group of rows applied at each refresh.

To find a command by its stable identifier, the registered test commands are studio.tests.run-all, studio.tests.run-selected, studio.tests.rerun-failed and studio.tests.repeat-selected. These identifiers are also useful when connecting a workbench action to the command registry.

4. Stop a long-running test

Choose Stop. Studio requests cancellation of the active CTest invocation and prevents later attempts in the selection from starting. The window stays open while the worker acknowledges that request and remaining completed rows are published.

Previously completed results are retained. A cancelled attempt is displayed as cancelled, not passed. Attempts that never started do not acquire invented success results. Pressing Stop after a test has already completed does not change its verified outcome.

When closing Studio during a pending run, the close guard requests Stop and leaves your documents open. Close again after the operation has finished; normal document-saving prompts still apply.

5. Read results and output

OutcomeMeaning
PassedThe selected test and its run/report checks succeeded.
FailedThe test or a required part of its CTest invocation failed. Read the failure details.
SkippedThe test was disabled or deliberately skipped. It did not pass.
CancelledCancellation interrupted the active attempt.
Timed outA configured deadline ended the attempt.
Not runThe attempt could not produce an executed result, for example because its executable was unavailable.

A compact output view keeps a labelled tail when the text is too long for the view. The service API UmiStudioTestRunResultAt provides the retained adapter result for the most recently accepted background run. Starting another accepted run or destroying the service releases that job's private result copies; the published history records remain in the Test Platform.

6. Practise with Umicom Notes

The repository includes framework/examples/testing/notes_project. Its tests check saving a note, retaining Unicode text and a longer indexing operation. The save operations use temporary files rather than your own notes.

Configure and build that project into build/notes-tests. Use that directory as the build root of its Studio profile, choose Debug, and discover its three tests. Run Save and Unicode first. Then run Index and press Stop while it is active. Finally, run Save again to check that the test service is ready for another operation.

The Framework guide framework/docs/QUEUED_TEST_RUNS.html contains complete PowerShell and Linux commands, a queued command-line runner and the C API source.

7. Handle changed projects and full history

Changing the active project, configuration or trust state while a run is pending requests Stop. A catalogue or history replacement also prevents further results from the old job being applied. This keeps results attached to the context that requested them. Rediscover the intended profile before running again.

A run may select up to 1,024 test identifiers. Repeated attempts must fit both the job's 4,096-attempt limit and the remaining 4,096-record result/output registries. A capacity error occurs before a new process is launched. Use a smaller selection or fewer repeats, or review the existing results and invoke studio.tests.clear-results and studio.tests.clear-output when those records are no longer needed.

Selection and clearing commands remain owner-thread operations. An extension must not edit Studio's service state from a worker thread.
